# Glossary

| Term | Definition | Status |
| --- | --- | --- |
| evidence-repair generation | An append-only successor generation created to observe previously indeterminate evidence without rewriting its predecessor. | local |
| schema-parity preflight | A versioned validator that enforces the frozen machine schema vocabulary before the existing semantic evaluator is called. | local |
| source-derived harness | An isolated executable model built from pinned source selectors and limited to declared decisions and observables. | local |
| baseline-equivalence witness | A passing comparison showing that the unmutated harness matches preregistered source-derived vectors over the bounded modeled surface. | local |
| mutation protocol | A frozen record of mutation ID, target, expected preserving or breaking consequence, vectors, observables, and stop conditions. | local |
| permitted screen substitution | M1 replacement of the step-9 screen adapter while preserving `onNext` and `onBack` interaction behavior. | local |
| breaking guard bypass | M2 replacement of guarded navigation commitment with direct requested-step commitment. | local |
| observation receipt | Immutable machine evidence from one mutation run, including input handles, vector results, consequence state, and uncertainty. | local |
| successor suite envelope | A suite result whose predecessor generation ID is the accepted generation-1 handle. | local |
| bounded fidelity | Agreement over declared vectors and observables only; never code, component, framework, or domain identity. | local |
| evidence repair | Work that supplies missing observations while preserving the hypothesis, rubric, and prior generation unchanged. | linked to parent calibration |
| residual support | The parent evaluator outcome requiring nonempty residue plus all frozen residual conditions; not identity or promotion. | linked to parent calibration |

## Linking Result

Parent calibration terms and outcome meanings are linked without redefinition.
Harness and successor-generation terms are local development vocabulary and are
not candidates for canonical DomainSpec promotion.
