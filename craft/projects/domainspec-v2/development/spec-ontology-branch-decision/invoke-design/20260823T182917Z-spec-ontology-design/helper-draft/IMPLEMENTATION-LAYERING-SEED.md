# Specification-Ontology Implementation Layering Seed

## Status and limit

This is a Design-phase layering seed, not a Plan, work pack, task list, SWU
decomposition, migration instruction, or implementation authorization.

## Proposed layers

| Layer | Responsibility | May depend on | Must not depend on or decide |
| --- | --- | --- | --- |
| `L0 owner authority` | current source, definitions, role, lifecycle, promotion, and publication decisions | existing owner-native evidence | generated projections or implementation behavior as source truth |
| `L1 structural protocol` | owner-qualified identity, version, digest, typed reference syntax | exact adopted syntax decision | record/relation meaning, discharge, promotion |
| `L2 owner-local branch models` | canonical business, formal/specification, proof-bridge, and system-evidence catalogs | L0 authority and L1 syntax | another branch's semantic payload as locally authored truth |
| `L3 cross-branch assertion contracts` | `formalizes`, two receipts, `derived_from`, derivation context, exact currentness | exact L2 endpoint refs and L0 owner routes | generated inverse edges or projections as authority |
| `L4 validation composition` | owner-local validator interfaces, integration checks, typed aggregate, negative corpus | L1-L3 exact manifests and validator owners | reinterpretation of owner meaning or lifecycle decisions |
| `L5 deterministic read models` | integrated graph, indexes, crosswalks, query and human views | exact admitted L2-L4 manifests, generator and policies | canonical authoring, discharge, promotion, publication grant |
| `L6 lifecycle integrations` | separately authorized adoption, evaluation, discharge, promotion, and publication receipts | exact L0-L5 subject digests and owner decisions | inferred transitions or broadened scope |

## Branch module boundaries

- `business`: source records and fidelity receipt adapter only.
- `formal-claims-specification`: claim, formalization, specification, membership,
  and formal assertion receipt contracts.
- `proof-bridge`: obligation, derivation edge, immutable context manifest, and
  lifecycle-input contracts.
- `system-evidence`: artifact, execution, observation, checker, and evaluator
  records.
- `integration`: relation/provenance validators and aggregate orchestration,
  without owner semantic implementations.
- `projection`: pure deterministic compilers and visible non-authority outputs.

Physical paths, package boundaries, schemas, language, and runtime remain
unselected. A later Plan must derive them from accepted contract bytes rather
than harden this seed by assumption.

## Dependency direction

```text
owner authority -> structural protocol -> owner-local catalogs
                                      -> cross-branch assertions
                                      -> validation composition
                                      -> deterministic read models

exact lifecycle owner decisions reference all required subjects;
they are not generated by the dependency chain.
```

Canonical inputs never depend on projections. Owner semantic validators are
invoked by integration but are not implemented inside a central validator.
Evidence records reference obligations; they do not mutate claims or set
discharge state.

## Compatibility and migration seam

The current financial-settlement prototype has three branches and locates
`business.FormalClause` in business. A future compatibility adapter may read
that exact frozen preimage and emit a candidate four-branch postimage, but the
adapter output remains a migration candidate until all affected owners accept
exact identity mappings and digests. No compatibility alias may become a
second canonical proposition.

## Layering acceptance questions for a later authorized route

- Which existing owner surface adopts the structural syntax exact bytes?
- Which exact definition and relationship signatures admit the candidate node
  and relation kinds?
- Where do owner-local canonical catalogs live after owner admission?
- Which runtime and package boundaries implement each owner validator without
  importing private authority into public code?
- Which lifecycle owner interfaces are external and therefore represented only
  by exact receipts?

These are downstream owner and Plan inputs, not open architecture alternatives.
