# Distill Result: Implementation Conformance Design Unit

## Run Frame

- Target context: one DomainSpec v2 Design package that can later support
  TypeScript, Python, and Rust without collapsing authority or native tooling.
- Objective and output artifact: reduce the architecture to the smallest
  coherent unit and prove recomposition; Design validation artifact.
- Mode and budget: Standard, assumed because no explicit Distill budget was
  selected; one proposal track, Proposer/Balancer roles, two rounds.
- Role execution: parent-simulated labeled roles. A second native helper would
  have required a newly shown and confirmed governed multi-agent dispatch; that
  authorization was not inferred.

## Role Conversation Trace

### Round 1

**Proposer claim:** use one governed contract family containing a language-neutral
contract/kernel boundary, three native adapter profiles, and shared fixtures.

**Evidence/assumption:** the accepted research requires shared normalized meaning
but assigns source parsing, type guarantees, and runtime execution to native
owners. TypeScript, Python, and Rust have incompatible export and source-graph
semantics.

**Balancer objections:**

| Category | Objection |
| --- | --- |
| cognitive load | contracts, core, three adapters, fixtures, migration, and authority could become an artificial seven-package taxonomy |
| hidden coupling | “shared core” hides the unselected implementation host and adapter transport |
| requisite variety | one parser or one-file/export law cannot absorb three language models |
| responsibility | migration and authority are external lifecycle concerns, not runtime components |

**Reconciliation:** retain one Design package and logical package family, but
select the kernel contract as the coherent unit. Keep adapters as separately
owned providers, fixtures as validation boundary objects, and migration/authority
as external routes. Do not select runtime package count or host in Design.

### Round 2

**Proposer claim:** the kernel closes over exact owner-bound inputs and returns
deterministic receipt material; it needs no filesystem, runner, store, scheduler,
or authority API.

**Evidence/assumption:** `ImplementationConformanceAPI`, binding reconciliation,
native normalization, runtime-evidence comparison, and receipt mapping provide
named inputs/outputs and a recomposition path through versioned provider contracts.

**Balancer objections:**

| Category | Objection |
| --- | --- |
| lifecycle contradiction | the Define State view does not distinguish invalid-envelope rejection from a valid failing receipt |
| authority dependency | edge policy, State Machine profile admission, and code-tag reformulation remain unresolved owners |
| implementation split | a core host or multi-language parity strategy is still unselected |

**Reconciliation:** the architecture unit is coherent for Design, but normal Plan
readiness is flagged. Record the upstream lifecycle clarification and owner gates;
do not create a Work Pack or pretend the host decision is cosmetic.

## Selected Unit

**Current smallest coherent unit:** Implementation Conformance Evaluation Kernel
Contract.

**Responsibility:** validate exact immutable owner inputs, reconcile one canonical
concept to one current implementation entry, normalize complete native evidence,
compare selected runtime-contract evidence, and return deterministic
non-authoritative receipt material.

**Inputs:** implementation profile, semantic owner refs/digests, code-tag mapping
projection, architecture findings, existing obligations, native bundles, optional
runtime fixture evidence.

**Outputs:** exact bindings/coverage, typed normalized findings, unsupported/skipped
residue, raw-evidence references, and generated receipt material with claim limits.

**Abstraction level:** capability with explicit interface and workflow contracts.

## Concept Layer Map

```text
purpose: implementation evidence agrees with admitted typed intent
  -> capability: implementation-conformance package family
    -> selected coherent unit: evaluation kernel contract
      -> functions: binding reconciliation, normalization, runtime comparison, receipt construction
    -> provider interfaces: TypeScript, Python, Rust adapters
    -> validation boundary object: shared witness/validator contracts
  -> external lifecycle: admission, migration, exception, promotion, release
```

## Closure And Recomposition Proof

The kernel closes because every responsibility has named immutable inputs, a
total result, and no hidden side effect. It recomposes upward when a project
integration supplies versioned owner resolvers and one or more language adapters;
the resulting receipt is then consumed by queries and an external authority
route. The named adapter envelope is the only coordination boundary. Runtime
execution, persistence, migration, and authority are not hidden glue.

Splitting binding reconciliation from normalization into separate governed
packages would add coordination without independent authority or lifecycle.
Merging adapters into the kernel would hide language effects. The selected unit
is therefore the responsible optimization point.

## Evolution Profile

- Concrete variants: TypeScript, Python, Rust, and future language adapters.
- Concrete policy growth: additional source classes, Rule-edge policies, and
  obligation kinds.
- Concrete migration pressure: code-tag reformulation and old projection rows.
- Likely integration growth: generated code, monorepos, FFI/RPC/plugin boundaries.
- Governance pressure: profile admission, exception owner, data handling, and
  receipt consumers.

Smallest extension boundary: versioned language adapter and owner-provider
contracts plus golden normalized fixtures. Deferred mechanisms: network service,
general parser platform, scheduler, persistent receipt service, general waiver
system, binding-selection engine, and broad Rust source graph.

## Premortem

Six months later, the design most likely failed because “shared evaluator” became
either a TypeScript tool runner that owns Python/Rust process behavior or three
drifting evaluator implementations with incomparable receipts. Category: hidden
coupling and too broad to validate. Guardrail: keep the kernel pure, bind adapter
envelopes by version/digest, select a host/parity strategy explicitly, and require
golden cross-language contract fixtures before parity claims.

## Frame Expiry

Rerun Distill when any of these becomes true:

- a core implementation host or multi-implementation parity strategy is selected;
- persistence, network transport, multiple implementation selection, FFI/RPC,
  or general exception acceptance enters scope;
- the profile admits general Rust macros/generated modules or new languages;
- runtime claims expand to durable state, concurrency, effect delivery, retries,
  idempotency, or compensation.

The first deferred complexity to revisit is the core host/parity boundary.
