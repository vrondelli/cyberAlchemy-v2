# Explicit EVF migration binding

Definitions and agent-facing ontology scaffolds: inherit L01's Retain, Adapt,
Compatibility envelope and Obligation correspondence concepts. No registered
ontology selectors or runtime admission are dependencies.

Product prototype: the caller selects `evf-s1-migration-002` to derive the existing
single EVF S1 obligation from the current verified key-and-door fixture. The old
`evf-s1` route keeps its historical behavior. Business prototype: consumers can
verify compatibility before any caller is switched or legacy binding retired.
DomainSpec prototype: L01-T06 requires full identity/payload equality and stale
reference rejection; T11 requires the actual previous entry point to remain usable.

Compiled-system prototype: the existing Minted Project compiler rebuilds graph
and provenance in memory; output must equal the selected generated bytes. The
existing EVF loader checks predicate/fixture/runtime/O_spec pins. The successor
changes only generated_graph and generated_source_manifest refs. Binding ID and
all semantic fields remain unchanged to preserve the exact native obligation.
Candidate identity lives in the outer migration profile and is not an authority
or replacement for the legacy binding identity.

Implementation: a fixed profile pins the successor binding and selected source
manifest. The bridge verifies those hashes, then all selected sources, verifies
the precise two-ref delta and reproducible compiler outputs, and passes the
explicit bundle to the existing native deriver. A second source check precedes
return. Rejection emits diagnostics and no obligations. No runtime pin refresh,
output-file mutation, fallback or materialization occurs. The code and profile
are bound by the candidate output manifest; this is local candidate integrity,
not protection against an attacker replacing the whole implementation.

The historical binding remains stale and is expected to reject. Its failed
receipt remains historical. This successor's tests establish current local
migration correspondence only. L03 owns all-row closure; L04 owns independent
review and product approval. Operational cutover and UI remain deferred.
