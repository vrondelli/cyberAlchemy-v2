Backend Test Engine: validated design and implementation path

The Backend Test Engine carries validated DomainSpec sources through graph construction, exact test derivation, execution, mutation, and independent replay. Profile admission and release remain external decisions.

Reusable kernel and adapter exist Design validated · implementation open Invoke Plan is next Jump to the live example ↓

How to read this implementation design

01 · THE IMPLEMENTATION IN ONE SENTENCE

One causal pipeline, four separated planes

Contracts say what is allowed. The compiler turns authored sources into one canonical graph. The proof system derives and executes exact checks. Consumers independently show the result remains usable without becoming DomainSpec authority.

02 · REUSABLE FOUNDATIONS

Existing compiler foundations

Reuse the strict YAML criterion kernel, minted-node body adapter, source hashing, compiler graph/manifest shape, deterministic utilities, and narrow receipt-verification patterns.

03 · IMPLEMENTATION SCOPE

Unimplemented proof spine

Add versioned replacement contracts, independent edge sources, minted-graph derivation, independent obligations, strict bindings and evaluators, execution/mutation evidence, complete receipts, replay, and fail-closed aggregates.

Completeness denominator

Reuse vs build

Design-defined code boundaries

The validated Design requires a new proof path connected to existing compiler primitives. Plan may choose concrete modules and filenames, but it must preserve these logical boundaries and forbidden dependencies.

Reuse and harden

  • meta-type-criteria.ts: parser, preflight, evaluator, stable violations.
  • meta-type-body-adapter.ts: node-body normalization and schema digest check.
  • resolver.ts: path containment, aliases, source hashing, canonical source-set digest.
  • compiler.ts: profile binding, node validation, deterministic graph/manifest output.
  • Existing keying, formal evaluation, deterministic serialization, and receipt-verification techniques where compatible.

Build as bounded modules

  • Versioned formation-replacement and JSON-retirement contract loaders.
  • Independent edge schema/root resolver and ordered graph model.
  • ProofContext resolver over the canonical graph, manifest, build, and governing handles.
  • O_spec validator, O_gen deriver, exact-set comparator.
  • Strict binding resolver, evaluator registry, test/mutation runner.
  • Causal receipt schema, replay verifier, core/consumer aggregate runners.

Do not carry forward

  • Current-v1 in-place widening or silent JSON retirement.
  • Node-embedded connections as the claimed independent-edge design.
  • Markdown/aspect parsing as minted graph authority.
  • First-match binding resolution.
  • Generated todo/skip as completeness evidence.
  • Count equality, literal pass fields, or producer-authored consumer receipts.

Reader terms

Plain language for the new architecture

Each definition states the term’s role, its proof value, and its misuse boundary.

Contracts, admissions, and authored inputs

Semantic contracts define allowed shape and meaning; owner decisions admit exact contracts or sets; authored inputs provide governed content. Derived graphs, evidence, aggregates, and lifecycle decisions remain separate roles.

Compiler plane

The source resolver, contract loader, validators, kernel, edge resolver, and graph builder. Why it matters: it is the only valid bridge from authored source to derivation input. Current code needs a successor path rather than in-place v1 widening.

Proof plane

The independent catalogue, derived obligations, exact comparison, tests, bindings, evaluators, runs, mutations, receipts, and replay. Why it matters: it detects omitted work rather than trusting a green summary. Most of this plane remains to build.

Normalized graph

The compiler’s deterministic generated node/edge view. Why it matters: all derivation sees one canonical input. It is a read model, not authored authority, and it is different from the legacy Markdown-derived ConceptGraph.

Source manifest

The join from graph IDs to exact source paths and hashes. Why it matters: every proof result can be traced to authored bytes. A graph item without a source join is an error.

ProofContext

An immutable envelope of exact profile, registry, formation, compiler, source-set, graph, manifest, and build handles. Why it matters: every proof record shares one complete context without copying or replacing the canonical graph.

Independent catalogue

The expected obligation set, frozen outside the generator implementation. Why it matters: a bug cannot shrink both output and denominator. The engine reads it but cannot overwrite it.

Binding and evaluator

A binding uniquely selects the runtime target and fixture; the evaluator independently judges one bounded claim. Why it matters: a test must say what it runs and who judges it. First-match selection and universal-oracle claims are forbidden.

Mutation

One declared semantic edit in a fresh child build, expected to trigger a named failure or remove a named causal effect. Why it matters: it proves the check distinguishes the intended defect. A stale digest or unrelated earlier error does not kill the targeted mutant.

Receipt and replay

The ProofReceipt indexes the causal identity/digest chain; a separate ReplayResult recomputes raw schemas, handles, joins, observations, and exact sets. Why it matters: stale or self-asserted evidence fails even when a stored field says pass. Neither one grants admission.

Exact-set proof

Compare the shared coverage key—catalogue ID plus obligation ID—not object shape or totals: O_spec = O_gen = T_gen = E_run = M_killed after projection. A blocking diff lists the exact missing, extra, duplicate, stale, or mismatched members. Why it matters: obligations, tests, results, and mutants retain different artifact IDs while incomplete coverage still fails.

Typed residue

A machine-readable blocking reason emitted when a required proof stage cannot complete. Why it matters: unsupported scope, missing bindings, stale evidence, and other failures remain explicit instead of becoming a generic pass or skip.

Core aggregate

The exact replay-backed, non-admitting structural result over all six BTE catalogues. Why it matters: consumers receive one verified core handle without gaining authority to redefine or admit DomainSpec.
