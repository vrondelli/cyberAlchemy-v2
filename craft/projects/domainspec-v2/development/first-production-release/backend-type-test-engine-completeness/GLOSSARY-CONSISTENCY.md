# Design Glossary Consistency

## Verdict

The Design keeps the meanings in [GLOSSARY.md](GLOSSARY.md) and adds precise
package-local distinctions needed for implementation. No term is promoted to
canonical DomainSpec vocabulary by this file.

## Refined Terms

| Term | Design meaning | Consistency rule |
| --- | --- | --- |
| `TestCase` | a pre-run instruction bundle targeting one obligation coverage key; it contains roles, fixtures, bindings required, and independent expectations | never call a post-run observation a test |
| `ExecutionResult` | a post-run bundle containing raw observations and a separate bounded evaluator verdict for the TestCase roles | never copy it back into the expected TestCase |
| artifact ID | the stable logical identity of one obligation, test, binding, result, mutation, receipt, or replay record | different record types keep different IDs |
| `coverage_key` | `catalogue_id + obligation_id`, the projection used to compare unlike O/T/E/M records | exact equality is over keys plus compatible versions/digests, not literal object equality |
| proof catalogue | one versioned, owner-frozen exact denominator whose members answer one proof question | catalogues are compared separately before aggregation |
| `D_structure` | 13 kind/schema structure-obligation bundles, one for each backend kind schema | it is distinct from `D_form=16` and cannot disappear inside a 16/16 result |
| static catalogue | a denominator fixed by a versioned contract, such as the 13 kinds or 16 criteria | never substitute graph-instance counts |
| instance catalogue | a denominator derived from one exact graph source set, such as its node or edge IDs | identity and membership are bound to the graph/source-set digest |
| selected | included in a design or planning set | does not mean admitted or implemented |
| candidate | has a concrete target identity or contract but lacks all owner gates/evidence | cannot enter a passing aggregate as admitted |
| admitted | explicitly approved by the owning lifecycle for an exact ID/version/digest | receipts and tests cannot perform this action |
| valid | conforms to its declared schema and semantic validator | does not imply admitted, green, or released |
| green | its bounded proof/evaluator verdict passed | does not imply authority, admission, or release |
| graph | the compiler-produced canonical normalized projection of the exact source set | derived read model, not authored authority |
| proof input envelope | typed handles to graph, manifest, build, profile, registries, and contracts | not a second graph; materialized rows must be lossless and bijective |
| `O_spec` | independently authored and frozen expected-obligation catalogue | may cite governing sources but cannot be generated by the BTE deriver |
| `O_gen` | obligation set derived from the canonical graph and admitted proof inputs | supplies subjects/anchors, never expected answers |
| Binding | explicit exact record joining one `(test_id, case_role)` to fixture, adapter, runtime, and evaluator handles | no predicate, subset, wildcard, or first-match meaning |
| Evaluator | independent comparator of raw observation against validation-owned expectation for one bounded interface | cannot import compiler/kernel/adapter/generator logic under test |
| mutation kill | expected semantic failure or causal-output removal produced by a fresh child lineage | stale digest failure by itself is not a kill |
| `ProofReceipt` | non-authoritative causal index over exact raw proof handles | not truth, replay, admission, or release |
| `ReplayResult` | separate replayer-owned result after raw handle/schema/digest/join/set recomputation | only successful replay may enter a passing aggregate |
| core aggregate | exact DomainSpec structural proof result | independent from consumer and UI execution |
| consumer aggregate | exact fresh IOLM and Body War replay result against one core handle | consumer evidence cannot define core truth |
| terminal BTE aggregate | exact composition of core and consumer aggregates | still non-admitting and non-releasing |

## Potentially Confusing Pairs

### Test versus result

The test says what to do and what outcome is expected **before** execution. The
result says what actually happened **after** execution. A test may exist without
a result; that condition is incomplete and fails the required set. A result
without its exact test and binding is orphan evidence and also fails.

### Equal sets versus equal objects

`Obligation`, `TestCase`, `ExecutionResult`, and `MutationResult` are different
objects and must not share an artifact ID. The equality statement means:

```text
Set(O_spec.coverage_key)
  = Set(O_gen.coverage_key)
  = Set(T_gen.coverage_key)
  = Set(E_run.coverage_key)
  = Set(M_killed.coverage_key)
```

Every joined record must also carry compatible governing versions and digests.
Equal counts with different keys, duplicates, or stale digests fail.

### Compiler validity versus proof completeness

A source can compile while BTE is incomplete. Compilation checks formation,
relationships, and graph construction. Completeness additionally requires the
independent catalogue, exact derivation, runnable tests, bindings, execution,
mutations, replay, and aggregates.

### YAML-owned versus “the current adapter is authority”

The accepted direction is a distinct versioned YAML-owned successor contract.
It does not promote today's adapter or change current v1. The successor becomes
admitted only after its structural grammar, retirement map, compatibility
corpus, source migration, implementation, and owner approval exist.

## No New Canonical Definitions

`coverage_key`, `proof catalogue`, `D_structure`, and the authority-class names
are local architecture vocabulary. If later work wants them outside this BTE
package, it must use definitions governance rather than copying this prose.
