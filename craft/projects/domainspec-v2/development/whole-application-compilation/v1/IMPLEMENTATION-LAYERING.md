# DomainSpec Whole-Application Compilation Implementation Layering

This plan joins the reconciled DomainSpec application compiler and the integration-generation v2 candidate into one exact, publishable, natively compilable application project.

Layer 0 is the smallest end-to-end proof. Later layers add language equivalence, CLI usability, provider realization, runtime evidence, and packaging without weakening earlier guarantees.

## Context

- Target: one DomainSpec source graph plus one integration source produces one coherent application project.
- Current state: partially implemented. Domain/application projects and integration projects are independently deterministic and natively compilable for TypeScript, Python, and Rust.
- Primary user: an application developer using the `domainspec-v2` CLI or package API.
- Primary constraint: preserve semantic separation and existing CLI compatibility while avoiding artifact, root-manifest, and module-index collisions.
- Existing application seam: `src/generation/project-instantiation.ts`, `src/generation/project-build.ts`, reconciled project planners, output layouts, atomic publication, and native verification.
- Existing integration seam: `src/system-integration/generation-v2.ts` and `integration-generation-source-v2.schema.json`.
- Existing exact integration candidate: `development/integration-reconciliation/v1/candidate/INTEGRATION-PRODUCT-CANDIDATE.v2.json`.

## Meaning of completion

The product claims are cumulative and must remain distinct:

| Claim | Required evidence |
| --- | --- |
| Whole-application formation | One closed plan binds domain and integration inputs and contains one collision-free artifact set. |
| Whole-application generation | One atomic publication contains exactly the planned application files and combined receipt. |
| Whole-application compilation | The published project passes its native TypeScript, Python, or Rust compiler from a clean consumer context. |
| Runnable reference application | A selected reference provider stack starts and accepts a bounded request. |
| Observed integration behavior | Provider-specific evidence establishes only the observed persistence, delivery, HTTP, or application stage. |
| Product candidate | Exact sources, generated bytes, test denominator, tools, environment, and claim ceiling are frozen. |

Generation or native compilation alone never establishes runtime behavior, deployment, provider selection, business completion, admission, publication, or release.

## Settled implementation choices

1. TypeScript, Python, and Rust remain the complete language denominator. Kotlin is not introduced.
2. No new domain meta-type is introduced for integration concepts.
3. The reconciled compiler path is the only new whole-application path. Legacy calls remain unchanged.
4. The additive CLI option is `--integration-source <absolute-json-file>`.
5. `--integration-source` is accepted by reconciled whole-project `instantiate-project`, `build`, `verify`, and `verify-project` commands.
6. Node-level `instantiate` rejects `--integration-source`; integration composition belongs to the whole project.
7. Integration generation gains an embedded contribution mode. Its existing standalone mode remains supported and byte-stable.
8. The whole-application composer, not either child generator, owns root manifests, module indexes, final path collision checks, and the combined receipt.
9. Source references are checked against the compiled DomainSpec graph before any artifact is published.
10. Provider selection remains explicit. Reference providers are never inferred or made defaults.
11. ORODI remains an observation-only projection with no return or control edge.
12. Publication remains atomic to a new target. No in-place merge or overwrite is introduced.

## Target command surface

Generation of a complete project:

```bash
domainspec-v2 instantiate-project "$SOURCE_ROOT" \
  --languages typescript \
  --target-root "$TARGET_ROOT" \
  --compilation-selection "$SELECTION_JSON" \
  --integration-source "$INTEGRATION_JSON"
```

Application-layout build:

```bash
domainspec-v2 build "$SOURCE_ROOT" \
  --language typescript \
  --target-root "$TARGET_ROOT" \
  --output-layout domainspec.project-layout/v1 \
  --compilation-selection "$SELECTION_JSON" \
  --integration-source "$INTEGRATION_JSON"
```

Native verification uses the existing language-specific tool arguments and the same integration source:

```bash
domainspec-v2 verify-project "$SOURCE_ROOT" \
  --target-root "$TARGET_ROOT" \
  --typescript-root "$TYPESCRIPT_ROOT" \
  --node-type-root "$NODE_TYPES_ROOT" \
  --lean-executable "$LEAN" \
  --compilation-selection "$SELECTION_JSON" \
  --integration-source "$INTEGRATION_JSON"
```

## Composition architecture

```text
DomainSpec source root ----> compiled project graph ----> reconciled application plan --\
                                                                                         +--> whole-application composer --> exact artifact set
Integration source JSON --> validated integration graph --> embedded contribution ------/
                                                                                                      |
                                                                                                      +--> combined receipt
                                                                                                      +--> atomic publication
                                                                                                      +--> native verification
```

The implementation introduces four bounded contracts:

### 1. Application-to-integration binding

`validateApplicationIntegrationBinding(graph, integration)` checks typed cross-graph references. At minimum it proves:

- logical persistence subjects resolve to declared Entity, Value Object, Enum, Sum, or supported field shapes;
- application dependency contracts resolve to declared Interface boundaries;
- operation references resolve to declared Operation nodes;
- event references resolve to Event nodes;
- mapper references resolve to Mapping nodes;
- mapped input and result references agree with their declared application boundary;
- referenced failure outcomes exist in the applicable operation or contract surface;
- no provider identifier is accepted as domain meaning;
- every join is exact and case-sensitive, with no suffix or unqualified fallback.

Its result binds the domain source-manifest digest, integration source digest, cross-graph joins, and `authority_effect: none`.

### 2. Embedded integration contribution

`planEmbeddedIntegrationContributionV1(source, language)` reuses the current validators and semantic manifest but returns:

- responsibility-owned source artifacts;
- root-manifest dependency contributions;
- module-index contributions;
- integration semantic manifest;
- integration plan digest;
- no standalone root manifest;
- no duplicate root module index;
- no publication behavior.

Standalone `planIntegrationProjectV2` keeps its existing output.

### 3. Whole-application artifact composer

`composeWholeApplicationPlanV1(applicationPlan, integrationContribution, binding)`:

- accepts only registered, freshly formed child plans;
- assigns every path to one owner;
- rejects exact and case-folded path collisions;
- composes root manifests deterministically;
- composes Rust and Python module indexes structurally rather than by string append;
- rewrites and validates imports against final projected paths;
- requires complete import closure;
- carries both child digests without changing either child plan;
- sorts the final artifact inventory deterministically;
- produces one `domainspec.whole-application-plan/v1-candidate` digest.

### 4. Combined publication and verification receipt

The receipt records:

- DomainSpec source-manifest digest;
- compilation-selection digest;
- integration-source digest;
- application-plan digest;
- integration-plan digest;
- cross-graph binding digest;
- output-layout definition digest;
- final artifact inventory and hashes;
- native verification tool identities and results when verification is requested;
- `runtime_guarantees_observed: false` until runtime evidence exists;
- `authority_effect: none`.

## Artifact ownership

| Artifact family | Owner | Composition rule |
| --- | --- | --- |
| Domain and application modules | Reconciled application planner | Preserved, with only existing layout projection. |
| Integration dependency contracts | Embedded integration planner | Must reference, not redefine, resolved domain types. |
| Provider adapters | Embedded integration planner | Generated only for explicit provider realizations. |
| Mappings and serialization | Embedded integration planner | Mapper-owned conversions remain separate from calculations. |
| Configuration and credential references | Embedded integration planner | References only; secret values are forbidden. |
| Database migrations | Embedded integration planner | Versioned and ordered; execution is deferred. |
| Observation adapters | Embedded integration planner | One-way, disclosure-bounded ORODI projection. |
| `tsconfig.json`, `pyproject.toml`, `Cargo.toml` | Whole-application composer | One deterministic root manifest per language. |
| Python package indexes and Rust `mod.rs`/`lib.rs` | Whole-application composer | Structural union with collision and import checks. |
| Semantic manifests | Respective child planners | Retained under `.domainspec`; hashes bound by combined receipt. |
| Final publication receipt | Whole-application composer | One exact receipt for the complete target. |

## Layer decision table

| Layer | Decision question | Minimum working unit | User outcome | Risk reduced | Promotion decision |
| --- | --- | --- | --- | --- | --- |

| L1 | After this layer, we know whether whole-application compilation is repeatable through the public CLI for all supported languages. | Python and Rust composition, CLI option, atomic publication, exact verification. | One CLI workflow generates and verifies a complete TypeScript, Python, or Rust project. | Cross-language drift, CLI compatibility, publication, and clean-consumer risk. | Continue only when all three native compilers pass from disposable roots. |
| L2 | After this layer, we know whether explicitly selected provider realizations can produce runnable adapter code without redefining domain meaning. | Reference PostgreSQL, NATS JetStream, inbound/outbound HTTP, migration and bootstrap contributions. | Generated application can be configured with a concrete reference stack. | Descriptor-only generation, dependency, startup, configuration, and secret-boundary risk. | Continue only if generated adapters compile and provider selection remains explicit. |

## Layer definitions

### L0 — TypeScript minimum whole-application proof

Included:

- closed application-to-integration binding schema and validator;
- a joined commerce fixture whose Entity, Interface, Operation, Event, Mapping, and failure references exist in the DomainSpec graph;
- embedded TypeScript integration contribution;
- deterministic root `tsconfig.json` composition;
- exact and case-folded collision rejection;
- final import-closure validation;
- pure `planWholeApplicationV1` package API;
- repeated and multiprocess determinism test;
- native `tsc --noEmit` in a disposable directory.

Deferred:

- CLI mutation;
- Python and Rust;
- concrete provider libraries;
- startup, migrations, database calls, broker calls, HTTP calls, and ORODI evaluation;
- packaging or release claims.

Exit evidence:

- valid commerce source forms one plan;
- every integration reference has one typed domain target;
- hostile missing, wrong-kind, case-drifted, and ambiguous references fail;
- artifact ownership is total and collision-free;
- two processes produce identical plan and artifact digests;
- generated TypeScript passes its native compiler;
- no temporary project or copied dependency cache remains.

### L1 — Three-language CLI completion

Included:

- Python root/package composition and import checking;
- Rust Cargo and module-tree composition;
- `--integration-source` parsing on reconciled whole-project commands;
- fail-before-effect validation of option combinations and absolute paths;
- combined atomic publication and currentness verification;
- stronger `verify-project` native compilation for all three languages;
- installed/clean-consumer CLI test;
- exact backward-compatibility fixture proving calls without the option retain current outputs.

Deferred:

- concrete provider execution;
- infrastructure provisioning;
- production deployment and production guarantees.

Exit evidence:

- one joined source compiles under TypeScript, Python, and Rust;
- semantic binding manifests are equivalent across languages;
- target publication is atomic and exact;
- stale domain, integration, selection, layout, or artifact bytes fail verification;
- unsupported Kotlin and node-level integration options fail before source or target effects;
- legacy and reconciled calls without integration remain unchanged.

### L2 — Explicit reference provider realization

Included:

- provider-pack contract separate from domain and integration meaning;
- PostgreSQL 16 persistence adapters and migration runner;
- NATS JetStream realization for queue, topic, stream, and dead-letter semantics;
- outbound HTTP client and inbound webhook/server adapter;
- language-specific locked dependencies and bootstrap composition;
- configuration schemas and environment-variable credential slots;
- startup validation that reports missing configuration without exposing secrets;
- provider-specific failures projected through declared failure mappings.

The reference libraries are explicit provider-pack selections:

| Language | PostgreSQL | Messaging | HTTP |
| --- | --- | --- | --- |
| TypeScript | `pg` | `nats` | platform `fetch` plus Node HTTP server |
| Python | `psycopg` | `nats-py` | `httpx` plus Starlette |
| Rust | `sqlx` | `async-nats` | `reqwest` plus Axum |

These packs are examples and qualification targets, not inferred defaults.

Exit evidence:

- each selected pack produces concrete compilable adapter code;
- an unselected provider produces no dependency or code;
- configuration contains references and schemas, never credential values;
- migration, broker, and HTTP bootstrap modules are reachable from one application entry point;
- provider code cannot add or change domain rules, policies, workflows, or outcomes.

### L3 — Bounded real-runtime proof

Included:

- disposable PostgreSQL 16 and NATS JetStream containers;
- a local HTTP payment stub and signed webhook fixture;
- migration application in a fresh database;
- application startup and health check;
- one commerce operation that persists an order, publishes `OrderSubmitted`, and performs an outbound HTTP call;
- independent topic subscribers plus queue/acknowledgement evidence;
- failure cases for database rollback, provider rejection, retry classification, dead-letter routing, and invalid webhook signature;
- disclosure-bounded ORODI observation with a prohibited return edge;
- deterministic fixture cleanup and shared dependency caches outside output roots.

Exit evidence:

- native application starts from generated bytes;
- database state, transport evidence, HTTP evidence, and application receipts agree;
- provider acceptance, transport delivery, application commit, and business completion remain separate stages;
- D48 classifies failures while workflow/caller policy alone selects continuation;
- no fixture repository, container, database volume, or per-case dependency cache survives the run.

### L4 — Packaging and exact candidate

Included:

- integration schemas and whole-application schemas in the published package;
- provider packs and locked dependency metadata;
- joined commerce source, selections, integration source, expected manifests, and scenarios;
- user guide covering generation, compilation, configuration, startup, verification, and claim boundaries;
- clean-package allowlist and installed-package tests;
- exact candidate freezer and validator binding all source and generated bytes;
- release notes and compatibility statement.

Exit evidence:

- `npm pack` contains every documented file and no development residue;
- a fresh consumer installs the package and completes the documented TypeScript, Python, and Rust flows;
- exact candidate validation checks external definition bindings, source digest, generated artifacts, test denominator, compiler identities, and temporary disposal;
- product review receives a candidate with `authority_effect: none` and an explicit forbidden-inference list.

- positive joined-commerce formation;
- missing, extra, wrong-kind, case-drifted, and ambiguous reference rejection;
- Entity, Value Object, Enum, Sum, optional, list, set, Interface, Operation, Event, Mapping, Policy, Rule, Workflow, and State Machine preservation;
- provider/domain non-collapse;
- Event/Message non-collapse;
- queue/topic/stream/dead-letter non-collapse;
- mapper/calculation independence;
- D48 classification/continuation independence;
- ORODI no-return edge.

### Artifact composition

- exact and case-folded collision rejection;
- root manifest single ownership;
- Python package closure;
- Rust module closure;
- TypeScript/Python/Rust import closure;
- deterministic sorting and hashes;
- cross-process repeatability;
- child-plan immutability;
- output-layout projection;
- exact final artifact inventory.

### CLI and publication

- accepted whole-project command forms;
- duplicate, partial, relative, unknown, and conflicting option rejection before effects;
- node-level integration rejection;
- no-option backward compatibility;
- atomic new-target publication;
- stale-source, stale-selection, stale-integration, stale-layout, and target-drift failure;
- single structured stdout result and stable diagnostics;

### Native and runtime

- TypeScript, Python, and Rust clean compile;
- selected provider dependency closure;
- application startup;
- PostgreSQL migration and commit/rollback;
- queue/topic/stream/dead-letter evidence;
- outbound HTTP and inbound signed webhook;
- bounded runtime receipts and disclosure;
- no runtime claim inflation;
- no leaked fixture resources or secrets.

## Non-regression guardrails

- Existing CLI invocations without `--integration-source` retain their current behavior and generated bytes.
- The standalone integration planner retains its current artifacts and digests.
- No generic `runtime/` integration directory is introduced into project layout.
- No universal `Port` abstraction is introduced.
- No provider redefines domain concepts, rules, policies, workflows, or outcomes.
- Calculations remain independent; mappers consume explicit results when needed.
- Queue, topic, stream, and dead-letter remain distinct.
- Provider acceptance never implies delivery, application commit, or business completion.
- D48 remains classification-only.
- ORODI remains observation-only.
- All plans are deterministic, frozen, exact, non-authoritative data.
- Publication targets must be normalized, absolute, new, and atomically claimed.
- Tests use disposable roots and do not copy dependency caches into generated projects.

## Recommended execution boundary

Start with WAC-01 through WAC-04 only. This completes L0 and answers the highest-risk question: whether the existing application and integration compilers can share one typed graph and one artifact tree without semantic or structural collapse.

Do not begin provider packs during L0. If L0 passes, WAC-05 and WAC-06 can run in parallel, followed by the shared CLI/publication work. Whole-application native compilation for all three languages is achieved at the end of L1. Runnable provider behavior begins only at L2 and is evidenced at L3.

## Claim ceiling

This document is an implementation plan. It does not authorize release, publication, provider default selection, deployment, production use, or admission. Layer completion must be established by its stated exit evidence; passing an earlier layer cannot be reported as completion of a later one.
