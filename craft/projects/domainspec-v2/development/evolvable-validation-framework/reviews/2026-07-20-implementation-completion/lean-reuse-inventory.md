## Proof boundary

This inventory distinguishes four maturities:

- `PROVED`: a Lean declaration builds in the pinned repository. This proves only the declaration in its Lean model.
- `PROPOSAL`: prose or schema design explicitly not validated.
- `NEGATIVE`: a counterexample, collapse, or impossibility result.
- `INFRA`: build/CI/package mechanics, not a semantic theorem.

No Lean theorem below is running-v2 proof. `USE-NOW` means only that the pattern has a named current v2 seam and an executable acceptance test. `ADAPT-LATER` is used for L2/L3 material. Authority-lifecycle/governance work is rejected for this build goal.

## Adoptable minimum

The Lean scan does **not** justify adding Lean to the DomainSpec v2 runtime or calling any Lean artifact a DomainSpec DSL. The smallest defensible reuse is four implementation disciplines:

1. a named S1 aggregate target with an explicit proof boundary (`29400ed` plus the target-inclusion fixes);
2. a separating mutation family, attached to the existing key-and-door conformance seam (`ProbeTypology` as analogy only);
3. a count-preserving `enforces` mutant (`card_pushout_eq`/`no_addEquiv_pushout` pattern);
4. a fail-closed `needs_formal`/blocked receipt, treating missing or false semantics as a negative result rather than an allowed placeholder (`12b7dea`).

Everything else is either L2/L3 adaptation or a rejection. The current human decision in DEC-GCP-001 still controls whether S1 can produce a real executable predicate; reuse cannot remove that blocker.
