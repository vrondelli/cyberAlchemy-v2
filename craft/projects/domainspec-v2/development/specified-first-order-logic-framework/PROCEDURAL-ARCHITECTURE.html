DomainSpec · from intent to evidence

How can the requirement, the code, and the tests all look right—and still disagree?

One describes what somebody meant. One records what a developer built. One checks a few examples. They may be reviewed at different moments by different people. The difficult problem is not producing more documents. It is keeping the same meaning alive while an idea becomes software.

Before nodes · why DomainSpec exists

A player has a key. The door should open. Simple—until the meaning changes.

Imagine your team is building a small game. The first requirement says, “A player with a key can unlock the door.” Product writes the sentence, a developer writes the function, and a tester checks that the door opens. Everyone agrees.

Key-and-Door

Product’s note

A player with a key
can unlock the door.

This records the original idea in plain language.

The implementation

if (player.hasKey) {
  unlock(door)
}

This turns one interpretation of the sentence into executable code.

The test

player has a key
unlock succeeds

This checks one example chosen by the tester.

Now the rule changes: the player needs the matching key for that door. Product updates the requirement. The developer updates the code. The old test still uses the matching key, so it keeps passing—but it never checks what happens with the wrong key.

Nothing is obviously broken when inspected alone. The requirement reads well. The code compiles. The test passes. Yet the three files no longer carry the same complete meaning.

The obvious answer is “write better documentation”

Better documentation helps. More tests help too. But here is the strange part: every new document or test becomes another place where the meaning can slowly diverge. The team does not only need more descriptions. It needs one explicit model that those descriptions and checks can point back to.

This is where DomainSpec begins. DomainSpec is a repeatable way to turn what a team means into a connected model that both people and tools can inspect. Before asking how to write the code, it asks: what things exist in this domain, how are they related, and which rules must remain true?

From one sentence to a model you can inspect

Player ── performs ──→ UnlockDoor ── produces ──→ DoorUnlocked
                              ↑
                              │ enforces
                         HasKeyRule

The sentence has been separated into the things it was talking about: a player, an unlock action, an event, and a rule. The arrows make their relationships visible. Now a tool can ask whether the required parts exist, whether a connection is allowed, and which source introduced each part.

understand the domain→ build a connected model→ derive work and checks→ observe the result→ make disagreements visible

What DomainSpec is trying to preserve

  • the important concepts in the problem;
  • the relationships between those concepts;
  • the rules the software is expected to respect;
  • the path from those rules to specifications, tests, and code work;
  • the evidence needed to notice when reality has drifted from the model.

What DomainSpec does not do for you

  • invent the correct business meaning;
  • remove the need for product, engineering, or testing judgment;
  • guarantee that application code exists or behaves correctly;
  • make every part of the intended pipeline available today;
  • turn an explanatory model into release approval.

Honesty boundary: the current DomainSpec v2 tools implement useful slices of the larger idea; they do not make the entire intent-to-code pipeline available today. The rest of this page labels capabilities as current or planned.

Where DomainSpec fits in the larger private system

DomainSpec asks “what?”

What does the domain mean? What concepts, relationships, and rules should the software preserve?

Arcanum organizes “how?”

Which reusable capabilities, routes, and work sessions help people and agents perform the work?

Saturn closes the loop

What actually happened, where did reality drift from intent, and what evidence shows that a correction worked?

System-frame boundary: this three-part view describes the intended private architecture. DomainSpec and Saturn are not claimed here as publicly shipped products.

Start here · available today

What is a DomainSpec node?

A node is a small file that describes one important part of the software. In a key-and-door game, separate nodes can describe the player, the unlock action, the door-opened event, and the rule that says the player must have the key. Connecting those nodes creates a map of how that part of the software is supposed to work.

Current format · experimental

What does “domain” mean here? It means the subject your software handles: players and doors in a game, orders in a shop, or settlements in a financial system. It does not mean a website address.

First picture the nodes as connected boxes

Player ── performs ──→ UnlockDoor ── produces ──→ DoorUnlocked
                              ↑
                              │ enforces
                         HasKeyRule

This picture says: a player performs the unlock action, the action produces a door-unlocked event, and the has-key rule controls whether the action is allowed. Each box is a node. Each labeled arrow is a connection.

The node file is the source developers edit. Later sections call it the canonical source, which simply means it is the main version the compiler trusts. The graph, documentation, and receipts are rebuilt from these files instead of being edited by hand.

The same rule as a real node file

The current tools accept this HasKeyRule example. The intent explains the rule in plain English. The connections section links the rule to UnlockDoor. 

{
  "schema_version": "minted-node/v1",
  "node_id": "key-and-door.HasKeyRule",
  "feature_id": "key-and-door",
  "kind": "Rule",
  "intent": "Allow the unlock operation only when the player holds the key.",
  "body": {
    "formal_return_type": "boolean"
  },
  "connections": [
    {
      "edge_id": "key-and-door.edge.has-key-rule-enforces-unlock-door",
      "type": "enforces",
      "to": "key-and-door.UnlockDoor"
    }
  ]
}

The seven parts of the file

schema_version
Says which version of the node-file format is being used.
node_id
Gives the node a unique name so other nodes can point to it.
feature_id
Says which feature this node belongs to.
kind
Says what kind of thing it is: an entity, event, operation, or rule.
intent
Explains in plain English why the node exists.
body
Stores the extra details required for that kind of node.
connections
Lists the arrows from this node to other nodes: the connection name, its type, and where it points.

How nodes can be used now

What you can do today

  • Describe four kinds of things: an Entity such as a player, an Operation such as unlocking, an Event such as a door being unlocked, and a Rule such as requiring a key.
  • Connect them with three relationship types: performs, produces, and enforces.
  • Catch common mistakes, such as duplicate names, missing target nodes, invalid connections, or missing details.
  • Build a graph, generated documentation, a list of source files, and a receipt describing the build.
  • Detect when generated files are out of date or no longer match their sources.
  • Use the result for structural checks: does the required model exist, and are its parts connected correctly?

What it does not do yet

  • Write the application code for you.
  • Prove that the running application behaves correctly.
  • Support every future DomainSpec node or relationship type.
  • Store the formal logic rules shown later on this page; the current minted-node/v1 format does not support them.
  • Decide that a feature is ready to release to users.
write node files→ check nodes and connections→ build the graph and reports→ run structural checks

The rest of this page explains the next idea. A future node format could store precise behavior rules, turn those rules into test cases, run the application, and compare what happened with what the rule required. That future system is called DS-SFOL. It does not run yet.

System context

Next, ask two different questions

After the nodes are connected, we want to know two things. First: did we describe all the required parts and connect them correctly? Second: does the running application do what the description says? DomainSpec supplies the description. BTE checks the first question. The planned DS-SFOL system would check the second.

The compiler creates three useful helpers. The graph is a map of the nodes and connections. The source manifest lists the files used to build that map. The build receipt records which versions and content fingerprints were used. These helpers can always be rebuilt from the node files.

DomainSpec describes the expected model

Nodes name the important things in the domain and connections show how they relate. In the future design, a node could also carry a precise behavior rule instead of leaving a test generator to guess from prose.

BTE checks the shape of the model

The Backend-Type Test Engine asks whether the required nodes and connections exist and can be traced back to their source files. It checks the description, not the application’s business behavior. A BTE pass does not mean application code was generated or that the application works correctly.

DS-SFOL would check behavior

The planned framework would turn precise node rules into a limited set of test cases, run the application, and compare what happened with what the rule required. It would not repair a missing or invalid node model.

Local evidence vocabulary: “proof” means replayable linkage between specified intent and observed evidence—not a theorem-prover proof. “Residue” means a typed, recorded gap that prevents the claimed evidence chain from closing. These are explanatory usages; the package glossary and consistency record remain the local terminology owners.

write DomainSpec nodes→ build the graph→ check the model’s shape+ check application behavior→ pass or record a gap

Why keep the questions separate? A model can be complete even when the application code is missing or wrong. Application code can also appear to work while required parts of the model are missing. Passing one check never silently passes the other.

DomainSpec verification context

Structure and behavior are different checks

Both checks begin with the same DomainSpec model, but they answer different questions. BTE checks whether the description has the required parts. DS-SFOL would check a limited, declared set of application behaviors.

Separate evidence lanes

A Financial Settlement model might contain all of this:

Rule: settlement.total-is-conserved
Operation: calculate-settlement-total
Rule --[enforces]--> Operation
logic: gross = net + fee

“Generated structure” and “generated application code” are different claims

1. Authored DomainSpec sources

Canonical nodes, relationships, and structured logic authored as domain intent. These sources say what must exist and what behavior is meaningful.

2. Generated structural artifacts

The compiler derives the graph, source manifest, build receipt, and structural obligations consumed by BTE. “Generated” at this stage means generated evidence and read models—not application functions, classes, services, or binaries.

3. Application implementation

Executable product code such as calculateSettlementTotal. It may be handwritten or produced by a separate code-generation process. Its existence and behavior require evidence beyond structural formation.

BTE’s boundary: BTE checks that the required DomainSpec structure is represented and traceable in stage 2. It does not, by that fact alone, establish that stage 3 exists, compiles, can be invoked, or implements the specified behavior. Even when a structural obligation checks a code tag, instance, or binding, that establishes presence or addressability—not behavioral correctness.

BTE asks: was it formed correctly?

Does the Rule node exist?
Does the Operation node exist?
Is Rule --[enforces]--> Operation allowed by the current relationship rules?
Are required types, instances, and formations present?
Do graph, manifest, and build identities agree?

A BTE pass supports structural formation and traceability back to canonical sources. It cannot establish that calculateSettlementTotal(100, 3) returns the correct value.

DS-SFOL asks: does it behave correctly?

Was the clause independently required?
Can its structured expression be typed?
Was every finite case bound and executed?
Does observed behavior satisfy gross = net + fee?
Do all clause and evidence identities close exactly?

A DS-SFOL pass supports bounded behavioral conformance. It does not establish that every required DomainSpec node or backend formation exists.

States the architecture must keep separate

BTE passes; implementation is absent
Structural formation is evidenced. DS-SFOL is blocked or unrunnable because there is no implementation target to observe.
BTE passes; implementation returns the wrong result
Structure remains valid. DS-SFOL fails because observed behavior does not satisfy the node-owned clause.
BTE fails; implementation appears to work
An implementation observation may exist, but the complete DomainSpec evidence chain cannot close because required structure or traceability is missing.

The target is conjunction, not substitution: structural evidence ∧ behavioral evidence. Even together these are scoped verification evidence, not automatic release or promotion authority.

Runtime procedure

Follow the clause through ten transformations

1

The target node extension owns the behavioral meaning

In the planned DS-SFOL extension, the rule is stored as a logic clause—a stable node-owned predicate, invariant, function definition, transition, or effect relation—inside its canonical behavioral node:

Target design, not current syntax: the current minted-node/v1 schema accepts the Rule formation shown earlier, but it does not accept body.logic. The following payload must first be admitted through a versioned canonical node-schema extension. 

body:
  logic:
    version: domainspec-node-logic/v1
    clauses:
      - id: settlement.total-is-conserved
        parameters: [gross, net, fee]
        expression:
          equals:
            - gross
            - add: [net, fee]

DS-SFOL must not discover this by reading Markdown or interpreting prose. If the node contains only: 

The settlement total should be correct.

then DS-SFOL reports needs-formal; it does not invent a formula.

2

An independent manifest declares what must be proven

Before test generation, a validation-owned manifest says:

Required clauses:
- settlement.total-is-conserved

This becomes the denominator: the independently constructed exact set of required proofs.

That matters because otherwise the generator could accidentally omit the clause and still report:

Generated 0 of 0 tests — success

With the denominator, that becomes:

Required:  1
Generated: 0
Verdict:   FAIL — missing clause
3

The canonical compiler builds the proof context

Using an admitted profile—the exact versioned language features, clause kinds, harness kinds, and residue rules allowed for this run—the node compiler produces one digest-bound compilation package: 

canonical node sources
        ↓
graph
source manifest
build receipt
source and profile digests

DS-SFOL consumes these products. It does not reopen node files or construct a second interpretation of the graph.

4

The node adapter projects the logic

The adapter extracts a NodeLogicEnvelope: the lossless package that joins node logic to compiled graph, manifest, build, profile, and source-set identities. 

node identity
module identity
clause identity
structured expression
graph digest
manifest digest
build digest
profile digest

This preserves the complete chain back to the canonical node. If the graph says one thing while the build receipt refers to an older source digest, projection fails as stale evidence.

5

The language kernel validates and typechecks it

The compiler determines that:

gross : Money
net   : Money
fee   : Money

add(Money, Money) → Money
equals(Money, Money) → Boolean

It then produces a typed expression:

equals(gross, add(net, fee))

Money and rational values use exact arithmetic. They should not silently become floating-point values. Unsupported or ambiguous logic produces an indeterminate result—a typed record that evaluation is missing or unsupported—and therefore failing residue; it does not become a skipped test.

6

Finite fixtures become executable cases

A validation-owned fixture universe—the explicitly declared finite values used to instantiate variables, quantifiers, and boundary cases—supplies: 

gross: 103
net: 100
fee: 3

The case deriver creates something conceptually like:

case ID: settlement.total-is-conserved/case-001
clause:  settlement.total-is-conserved
inputs:  net=100, fee=3
observed role: gross
fixture digest: …

Quantifiers are handled similarly, but only over declared finite universes:

forall settlement in admitted-settlement-fixtures

There is no unbounded search.

7

Connect the case to implementation code

A binding is a non-authoritative invocation map from one derived execution role to exactly one implementation symbol or harness. It might say: 

role: calculate-settlement-total
module: financial-settlement/calculator
symbol: calculateSettlementTotal
arguments: [net, fee]

Critically, it cannot say:

expected: 103

The binding owns invocation mechanics, not truth.

8

The runner observes reality

The runner calls:

calculateSettlementTotal(100, 3)

Suppose the implementation returns:

103

The runner records a raw observation—the unjudged value or effect trace produced by the implementation: 

arguments: [100, 3]
raw return: 103
target digest: …
runtime version: …

It does not declare that 103 is correct.

9

The evaluator calculates meaning independently

Separately, DS-SFOL evaluates:

net + fee
100 + 3
103

It then compares the independently derived result with the raw implementation observation: 

specified result: 103
observed result:  103
verdict: pass

If the implementation returns 102:

specified result: 103
observed result:  102
verdict: fail

The evaluator is forbidden from importing or calling calculateSettlementTotal. Otherwise the system would grade the implementation using the implementation itself.

10

Compare the complete evidence chain

The proof join is the final exact-identity comparison. It checks the complete evidence chain: 

required clauses
= projected clauses
= validated clauses
= typed clauses
= generated cases
= bound cases
= executed observations
= evaluated results

In the specification this is expressed as:

Cspec = Cprojected = Cvalidated = Ctyped
= Tgenerated = Cbound = Orun = Revaluated

Equal counts are insufficient. The identities and compatible digests must also match.

The final receipt binds together:

canonical node
+ canonical build
+ denominator member
+ typed expression
+ fixture
+ generated case
+ binding
+ implementation digest
+ raw observation
+ evaluation
+ replay result

Mental model

The architecture as three independent streams

The simplest mental model is:

ACCOUNTABILITY admission manifest ───────────────→ exact denominator
MEANING canonical node → typed clause → expected meaning
REALITY binding → implementation → observation
independent join → proof or residue

Expected meaning flows from the node and fixtures. Observed behavior flows from the implementation. Accountability independently says what must exist. They meet only at the proof join.

Separation of authority

No participant controls both the question and its answer

The separation is intentional:

Source owner
Controls meaning.
Validation owner
Controls what must be covered and the fixture universe.
Implementation owner
Controls executable code.
Runner
Records reality.
Evaluator
Judges meaning independently.
Proof join
Establishes exact completeness.

Effectful example

A return value cannot prove state, calls, or events

A return value is insufficient for a rule such as:

When a pending settlement is confirmed:
- state becomes SETTLED;
- the gateway is called once;
- SettlementCompleted is emitted once.

An effect harness—an execution adapter that records explicit state, calls, writes, events, and errors—records: 

pre-state:
  status: PENDING

calls:
  gateway.confirm(settlement-123)

writes:
  status: SETTLED

events:
  SettlementCompleted(settlement-123)

errors: []

post-state:
  status: SETTLED

The evaluator checks the node-owned effect relation against this trace.

Examples of failures:

state changed, but event missing       → fail
event emitted twice                    → fail
gateway called after event             → fail, if order is specified
trace does not capture gateway calls   → indeterminate → fail
teardown or containment failed         → fail

This is why DS-SFOL has two execution surfaces:

Pure runner

Invokes a deterministic function and records only its raw return or throw.

Effect harness

state, calls, writes, events, errors

Claim ceiling

Specified first-order logic is bounded

The target is an executable, deterministic domain-logic profile—not an arbitrary theorem prover.

It supports

  • typed terms and predicates;
  • exact integer and rational values;
  • finite named quantifier universes;
  • function definitions and effect relations;
  • deterministic resource-bounded evaluation;
  • typed indeterminate residue.

It does not claim

  • arbitrary satisfiability or validity solving;
  • unbounded quantification or recursive proof search;
  • automatic invention of business truth;
  • production correctness from generated tests alone;
  • release or promotion authority.

Two different orders

Runtime order versus implementation order

The finished runtime begins with the canonical node:

node→ compile→ project→ typecheck→ derive→ bind→ observe→ evaluate→ prove

Construction begins elsewhere:

L0

Denominator and language/evaluator.

L1

Pure bindings, execution, proof, and replay.

L2

Effects and canonical node adapter.

L3

Financial Settlement and a second adopter—another feature or product that supplies its own canonical logic, fixtures, bindings, and harness adapters.

The denominator is implemented first because the system needs an independent definition of “everything that must exist” before trusting generated tests.

What exists now

Complete as a plan, not as a running framework

Established

  • The current experimental minted-project package validates canonical minted-node/v1 sources and compiles structural graph, manifest, Markdown, and receipt read models.
  • The DS-SFOL architecture and twelve-SWU work pack are defined.
  • SWU-SFOL-001, the independent denominator, is mutation-ready.
  • Its staged package has 11 passing tests.

Not established yet

  • A versioned canonical node extension that admits body.logic has not yet been implemented.
  • The canonical denominator implementation files have not yet been applied.
  • The language, evaluator, bindings, runners, proof system, and node adapter remain future SWUs.
  • Financial Settlement adoption comes at L3.

The full procedural chain does not run yet. The immediate implementation step remains SWU-SFOL-001; Financial Settlement test generation becomes meaningful only after the core and canonical-node integration exist.

Procedure map

  2. Manifest declares coverage
  3. Compiler builds context
  4. Adapter projects logic
