DomainSpec v2 · DS-SFOL · procedural architecture

From a domain clause to executable evidence.

Start with one meaning owned by a canonical behavioral node. Carry it through bounded logic, a real implementation observation, independent evaluation, and an exact-set proof. Every handoff keeps its identity and digest.

The central idea: the implementation may produce the observed answer, but it never supplies the expected answer. The specification and the evaluator remain independent of the code under test.

01 · begin with behavior

One Financial Settlement example

This clause is deliberately simple so the architecture is visible. It is an explanatory example, not approved Financial Settlement authority or final DS-SFOL syntax.

illustrative

Meaning

settlement.total-is-conserved

For an admitted settlement fixture, the gross amount equals the net amount plus its fee.

gross = net + fee

Illustrative structured payload

body.logic:
  version: domainspec-node-logic/v1
  module: financial-settlement
  clauses:
    - id: settlement.total-is-conserved
      kind: predicate
      parameters: [gross, net, fee]
      expression:
        equals: [gross, { add: [net, fee] }]

DS-SFOL does not scrape this meaning from Markdown, a Formal table cell, or a fenced formula. Real logic must be structured data owned by the canonical node and preserved by the canonical graph/manifest/build process.

03 · two observation procedures

Pure answers and real-world effects need different evidence

A returned value cannot prove that state changed, a gateway was called, or an event was emitted.

pure

Example: calculate a settlement total

  1. Fixture supplies net=100 and fee=3.
  2. Binding calls calculateSettlementTotal.
  3. Runner records the raw return.
  4. Evaluator independently computes the specified expression.
  5. Proof joins the exact case and digests.
arguments: [100, 3] rawReturn: 103 expectedFromSpec: 103 verdict: pass
effectful

Example: confirm a settlement

  1. Fixture supplies a contained pending settlement.
  2. Harness captures pre-state, calls, writes, events, errors, and post-state.
  3. Implementation runs inside the declared containment boundary.
  4. Evaluator checks the node-owned transition/effect relation over the raw trace.
  5. Missing, extra, or out-of-order effects fail.
pre.state: PENDING calls: [gateway.confirm] post.state: SETTLED events: [SettlementCompleted] verdict: evaluated from relation

The effect example is also illustrative. The actual Financial Settlement owner must approve its exact clauses, fixture universe, and observation surface before L3 adoption.

06 · evidence lanes

Structural BTE and semantic DS-SFOL answer different questions

Both may later feed an admission decision. Neither can substitute for the other.

Structural BTE

“Is the required shape present?”

  • nodes and edges
  • tags and instances
  • backend forms and signatures
  • structural obligations

It does not prove: that a settlement calculation or transition behaves correctly.

Semantic DS-SFOL

“Does admitted behavior match meaning?”

  • node-owned structured clauses
  • finite cases and exact bindings
  • raw implementation observations
  • independent semantic verdicts

It does not prove: full feature, release, solver, or production completeness.

≠

A green structural suite is not a green semantic suite. The receipts and terminology remain separate.

07 · completeness rule

Exact sets—not matching counts

Two lists can both contain ten items while disagreeing about which ten. DS-SFOL joins stable identities and compatible digests.

Cspec = Cprojected = Cvalidated = Ctyped = Tgenerated = Cbound = Orun = Revaluated
No missing member.
A required clause cannot disappear between stages.
No extra member.
The generator cannot invent a clause and grade it as coverage.
No silent residue.
Skip, todo, stale, duplicate, unsupported, unbound, or indeterminate fails an admitted profile.

08 · claim ceiling

“Specified first-order logic” is deliberately bounded

The target is executable, deterministic domain logic—not general theorem proving.

DS-SFOL v1 is designed to support

  • typed terms and predicates
  • exact integers and rationals
  • finite named quantifier universes
  • function definitions and effect relations
  • deterministic resource-bounded evaluation
  • typed indeterminate residue

It does not claim

  • arbitrary satisfiability or validity solving
  • unbounded quantification or recursive proof search
  • automatic invention of business truth
  • SMT, Lean, Datalog, Cedar, Alloy, or TLA+ integration
  • production correctness from generated tests alone
  • release or promotion authority

09 · implementation procedure

The runtime begins at the node; construction begins at the denominator

This order establishes the trust boundaries before connecting real adopter behavior.

L0 · current

Prove the semantic kernel

  • SWU-001 denominator
  • AST and diagnostics
  • decoder and normalization
  • types and finite domains
  • independent evaluator

L1

Run pure behavior

  • exact-one bindings
  • finite case derivation
  • raw pure observation
  • proof receipts
  • replay

L2

Connect effects and nodes

  • typed effect traces
  • contained harness SPI
  • canonical node adapter
  • proof-context validation

L3

Demonstrate generality

  • Financial Settlement
  • Agent Execution Orchestrator
  • unchanged core contract
  • full replay and boundary audit

Why the denominator is first: if the same generator decides both which tests should exist and which tests do exist, it can omit a clause and still report itself complete. Independent accounting creates the first trustworthy red test.
