# Execution Pack

Execution is strictly sequential because each unit supplies an acceptance
boundary consumed by the next:

1. `SWU-SFOL-BC-001` — profile/compiler admission.
2. `SWU-SFOL-BC-002` — exact Financial Settlement experimental source proposal.
3. `SWU-SFOL-BC-003` — generic effect case/proof/replay vertical.
4. `SWU-SFOL-BC-004` — canonical Financial Settlement source and build.
5. `SWU-SFOL-BC-005` — consumer adoption proof.

This sequence is an execution policy, not a false causal dependency graph.
BC-003 depends on the prior framework effect/projection SWUs; BC-004 depends on
BC-001 and BC-002; BC-005 depends on BC-003 and BC-004.

Each Task Session executes one SWU and emits one terminal source receipt.
Closeout synchronization is a bounded
`invoke:refresh:apply-approved` hop over this package and the parent work pack.
The next SWU is returned, never recursively executed by the same Task Session.

Stop immediately on:

- source authority wider than the experimental proposed C3/P4 profile;
- changes to the released profile registry;
- expected values stored in an implementation binding or adapter;
- an effect adapter synthesizing write/event observations from a decision
  boolean instead of capturing the real GenerateSettlement use case;
- generated inputs bypassing canonical graph/manifest/build handles;
- effect evidence without exact-set receipt and replay;
- P4 no-effect converse claims without a separately admitted clause;
- nondeterministic generated bytes;
- any release, publication, or production claim.
