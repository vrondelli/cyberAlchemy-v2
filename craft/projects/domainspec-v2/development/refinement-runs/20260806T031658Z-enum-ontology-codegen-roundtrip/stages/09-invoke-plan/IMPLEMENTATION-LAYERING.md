# Implementation Layering — Enum Architecture Realization Compiler

## Boundary rule

Each layer answers one new question with evidence from the previous layer. No
later layer may repair missing semantic or authority evidence by inference.

| Layer | Question unlocked | In scope | Promotion evidence | Explicitly deferred |
|---|---|---|---|---|
| L0 — ontology and obligation denominator | Do exact ontology/profile sources describe the required direct Enum realization, and are independent inputs frozen before code generation? | red realization-spec fixture, projector, definition snapshot validator, snapshot-bound v2 obligation catalogue, TypeScript binding validator, and immutable v1 catalogue regression | exact ontology/profile handles; expected-red then green projector; schema-valid candidate definition/binding; exact snapshot byte/semantic join; same-key and definition-reference drift rejection; unchanged v1 validation | source emission, compilation, evaluation |
| L1 — positive realization path | Can the frozen semantic/architecture inputs deterministically produce and compile the admitted TypeScript runtime/type form without unsafe text or expectation leakage? | portable IR, safe emitter, mirrored workspace, independent type/runtime witnesses, no-expectations observation | deterministic source bytes; hostile-input deaths; pinned green compilation; exact literal union; owned runtime freeze; observed real generated bytes | architecture verdict, mutation, replay |
| L2 — independent proof closure | Can a separate evaluator detect semantic loss, bind all evidence, and reconstruct the exact result? | evaluator, forbidden imports, AST mutation, evidence state machine/writer, isolated replay, one end-to-end proof | positive exact evaluation; missing-`Paid` compile-green exact failure; one-node delta; atomic receipts; separate-process reconstruction; legacy nonregression | composition and language parity |
| L3 — scale and delivery | Is the mechanism ready to expand beyond the first proof? | decision-only exit assessment | owner decision based on L2 receipt | all direct obligations, composition, Python/Rust, cross-language parity, checked-in generation, package/release/deployment |

## Promotion gates

### L0 -> L1

- The ontology-derived spec enumerates every required property/operator and
  rejects one removed property fixture.
- Definition and binding snapshots are total, injective, digest-bound, and
  authority-bounded.
- The active independent v2 catalogue is derived only from the exact definition
  snapshot members and binds its source path, byte digest, and semantic digest.
- Same-key/changed-payload and isolated stale-definition-reference admission
  fail, while the historical v1 catalogue regression remains green.

### L1 -> L2

- Identical inputs produce byte-identical reparsed source.
- Hostile inputs cannot escape paths or inject TypeScript syntax.
- Exact pinned compilation, independent type witness, runtime values, and
  runtime frozen state pass.
- Generated-source observation contains no caller-supplied expectation oracle.

### L2 -> L3 assessment

- Positive obligation passes through the independent evaluator.
- Removing only `Paid` is a one-node AST delta, still compiles, and yields only
  `ARCH_ENUM_MEMBER_MISSING` for `status.paid`.
- Raw evidence is atomically published and independently replayed.
- Existing hand-authored TypeScript runner tests remain green.

## Deferral rule

L3 scope is not automatically admitted by L2 success. Composition requires
relation/alias observations; Python and Rust require separate target bindings,
emitters, compiler/runtime witnesses, and language-owner receipts. They may reuse
the portable IR and catalogue contracts only after an explicit follow-up design
check proves those contracts remained target-neutral.
