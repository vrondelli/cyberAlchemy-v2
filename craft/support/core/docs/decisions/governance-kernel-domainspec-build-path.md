## Decision question

Which implementation path should create the Governance kernel from DomainSpec
v2 rather than merely label handwritten Rust with DomainSpec meta-type names?

## Evidence boundary

- The canonical current implementation state names
  `domainspec-meta-types-current-implemented@4`.
- The executable private CLI and its receipts remain pinned to historical
  baseline `@3`.
- The Rust rows for Entity, Value Object, Enum, and Calculation are identical
  between `@3` and `@4`, but a new CLI receipt would still claim `@3`.
- The CLI generates one closed artifact per invocation and then requires exact
  generated bytes.
- Only Governance Verdict fits the current Rust Enum generator. The current
  Entity, Value Object, and Calculation generators cannot express the richer
  Governance Program, Request, Fact Set, or evaluator semantics.
- The DomainSpec CLI surface already contains unrelated modified and untracked
  owner work, so in-place mutation is unsafe.

## Admissible options

### 1. `EXTEND_DOMAINSPEC_IN_ISOLATED_WORKTREE` — recommended

First reconcile the CLI to baseline `@4` in an isolated worktree, then extend
the Rust generation and observation contracts for the required field and
calculation shapes. Instantiate the Governance source model only after those
contracts pass.

Benefit: this is the only path that can honestly establish that the whole
kernel was created and observed through DomainSpec v2 implementations.

Cost and risk: it is the largest path, changes DomainSpec implementation code,
and remains subject to the DomainSpec v2 meta-type implementation owner gate.
It should begin with generated Governance Verdict as the smallest wedge.

### 2. `BUILD_CANDIDATE_LOCAL_CONFORMANCE`

Keep the handwritten kernel in CyberAlchemy and add candidate-local bindings
and tests derived from the admitted Rust protocol obligations.

Benefit: fastest path, no DomainSpec core collision, and useful semantic
pressure on Program identity, value equality, verdict wire behavior, and
calculation purity.

Cost and risk: it would establish candidate conformance evidence only. It
would not establish that DomainSpec's CLI instantiated the kernel.

### 3. `DEFER_DOMAINSPEC_BUILD`

Keep the current passing no-effect Rust candidate and wait until the CLI's
`@4` baseline reconciliation is settled.

Benefit: preserves current owner work and avoids a misleading conformance
claim.

Cost and risk: the kernel remains handwritten and its DomainSpec table remains
a design mapping only.

## Rejected before presentation

`EXTEND_DOMAINSPEC_IN_PLACE` is structurally inadmissible because it would
overlap extensive modified and untracked DomainSpec implementation bytes in
the shared checkout.
