# Task Selection Contract

Status: `active`

The first live portfolio was selected on 2026-08-29 before condition outputs.
See [`TASK-PORTFOLIO.md`](TASK-PORTFOLIO.md) for the plain-language decision and
[`evidence/live-task-selection.json`](evidence/live-task-selection.json) for the
validated machine record.

## Sampling Frame

Create the candidate list before preparing condition materials. Candidate tasks
must come from repository work with stable source selectors and an owner who can
freeze intended meaning and hidden acceptance cases.

## Inclusion Rules

A task is eligible only when it:

- can run from one pinned repository commit in a local sandbox;
- has a bounded implementation surface suitable for one plan-to-implementation
  chain;
- has at least three hidden semantic acceptance cases;
- has a reviewable goal, intent, context, owner, allowed actions, and blocked
  actions;
- can be completed without credentials, deployment, publication, or network
  effects;
- is not drawn from work already completed by the selected model in this study;
- permits information-matched notes and pack representations; and
- has no secret or personal data in the experiment packet.

## Exclusion Rules

Exclude tasks that:

- require a product, authority, or architecture decision during the run;
- cannot distinguish semantic correctness from ordinary test success;
- need a live external integration;
- are selected after inspecting condition performance;
- depend on unstable generated bytes or active concurrent writers; or
- fall into the middle ambiguity band defined below.

## Ambiguity Rubric

Score each dimension before condition assignment:

| Dimension | 0 | 1 | 2 |
| --- | --- | --- | --- |
| concept meaning | explicit and single | incomplete but inferable | conflicting or consequentially unclear |
| context boundary | exact | one mild boundary question | multiple plausible scopes change behavior |
| ownership/authority | explicit | route known but not stated | wrong owner or permission assumption changes the result |
| valid outcome | implement is clearly required | limited uncertainty | implement, abstain, ask, or escalate materially compete |

Classification:

- `low_ambiguity_control`: total 0–1 and no dimension scores 2;
- `high_ambiguity`: total at least 4 and at least one dimension scores 2;
- total 2–3: exclude from the first pilot.

## Pre-Frozen Selection Record

For every candidate, record:

```text
candidate_id
repository_commit
source selectors
inclusion checks
exclusion checks
four ambiguity scores
classification
classification reason
selected: yes | no
selection reason
recorded_at
recorded_by
```

The machine record uses `evidence/task-selection.schema.json`. Validate it with
`evidence/validate_task_selection.py`. Its exact file digest is recorded as
`task_selection_digest` in every run row. The joined bundle validator rejects
rows or manifests that do not name the selected tasks.

Select exactly two low-ambiguity controls and four high-ambiguity tasks before
any condition output is inspected. Preserve rejected candidates and reasons.

## Order And Stochasticity

Use a recorded random seed to assign condition execution order independently
inside each task block. Use clean sessions and one fixed model/harness identity.
The first pilot has one run per cell; therefore it is exploratory and cannot
separate treatment effects from model stochasticity without a replication wave.
