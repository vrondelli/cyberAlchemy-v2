## System purpose

DomainSpec is a typed intent language and evidence system for describing a domain model, selecting an
exact implementation realization, materializing it into a target project, and independently checking that
the result conforms. The product is not just a code generator: its essential invariant is that a selected
meaning and realization remain identifiable from declaration through generated bytes and evidence.

## Logical architecture

```text
canonical definitions and product ontology
                    |
                    v
        immutable implemented baseline
                    |
                    v
 typed instance intent + exact realization selection
                    |
                    v
   deterministic materializer / target-project CLI
                    |
                    v
      generated project implementation bytes
                    |
                    v
 independent architecture-conformance providers
                    |
                    v
 locked, replayable evidence and explicit residue
                    |
                    v
       separately owned admission decisions
```

The arrows are dependency and evidence flow, not ownership collapse. Definitions decide meaning. A
baseline freezes current implemented choices. The CLI instantiates only a selected realization. The
conformance factory observes the result independently. Evidence informs a later owner decision; it does
not make that decision.

## Logical layers

| Layer | Responsibility | Current physical homes | Current state |
| --- | --- | --- | --- |
| L0 — language | Canonical terms, formation criteria, meta-type identities, and relationship meaning | `definitions/`, `ontology/`, `authority/` | Admitted and current, with historical development evidence retained |
| L1 — realization | Language-neutral contracts and TypeScript/Python/Rust realization selections | `formalization/`, `definitions/meta-types/`, `impl/architecture-conformance/` | Broadly implemented for three profiles; some late relationship and provider gates remain |
| L2 — instantiation | Decode instance intent, select the exact realization, plan writes, and materialize a package | `impl/`, `development/meta-type-instantiation-cli/` | Baseline and first CLI slices exist; target-project generation is the active frontier |
| L3 — target implementation | Concrete generated code, adapters, persistence/outbox bindings, and runtime infrastructure | Consuming project, plus reference fixtures under `impl/` | Reference witnesses exist; generic consuming-project materialization is not yet closed |
| L4 — observation | Independently run profile-aware conformance checks over locked target bytes | `impl/architecture-conformance/factory/` | Active factory with TypeScript, Python, and Rust providers and replayable receipts |
| L5 — evidence and decision | Normalize results, preserve residue, and route separately owned decisions | development evidence, authority decisions, EVF lanes | Many bounded proofs exist; one complete source-to-independent-consumer vertical is still open |

## Physical project areas

- `authority/` owns axioms, owner decisions, and admission evidence.
- `definitions/` owns canonical language and the admitted current implementation projection.
- `ontology/` publishes product and system graph views from admitted sources.
- `formalization/` owns language-neutral contracts and profile correspondences.
- `impl/` is the private executable implementation, CLI, generators, factory, fixtures, and tests.
- `architecture/` records reusable system architecture such as durable recovery.
- `development/` holds active continuations and bounded evidence; it is not canonical merely because it passes.
- `.craft/` is a navigation/read-model ledger; it cannot override owner decisions or terminal evidence.
- `research/` preserves source-first investigations that require explicit admission before use as canonical meaning.

## Current enforcement frontier

The current factory already registers reference providers across the three language profiles and has
specific Operation and Workflow fixtures. The admitted baseline and conformance surface are therefore
not the principal missing capability. The missing vertical is the consuming-project path:

1. accept one typed instance intent;
2. bind it to the exact admitted realization and baseline identity;
3. write deterministic target-project bytes through declared ports;
4. emit a manifest containing selected realization and content digests;
5. run independent conformance providers against those target bytes;
6. reject undeclared or mismatched relationships/effects; and
7. return a replayable receipt without claiming admission or release.

For Operation and Workflow, this includes the declared read/write/effect sets, pre-mutation guards,
state-and-outbox atomicity, explicit failure continuation, undeclared-effect rejection, relationship
constraints to Rule/Event/Workflow, and durable recovery bindings where the design requires them.

## Observed versus recommended

Observed current state is captured in the [project map](../PROJECT-MAP.md) and exact evidence links.
Recommended migration structure is only a packaging recommendation:

- preserve canonical areas as exact working bytes;
- preserve `impl/` as the active executable dependency;
- carry active and blocked development packages as non-canonical continuations;
- preserve completed evidence without promoting it into runtime;
- archive superseded and historical provenance outside the active successor surface; and
- regenerate only derived map/receipt views, never the product implementation itself.

The recommendation becomes executable only after an exact target layout, copy inventory, and validation
closure are separately authored and accepted.
