## Outcome, claim ceiling, and decision

For each *explicitly selected* client/conversation, the path is client -> ARE
gateway -> selected harness backend -> model. ARE owns one authenticated
conversation writer and the pre-dispatch objective/context/effect decision;
the harness retains its documented backend/session responsibilities. A receipt
or status panel without exclusive ingress is not control. A distinct
ARE-hosted client may reach this outcome before a stock app does, but must not
be advertised as stock-app New Chat/Web integration. Existing-chat takeover
is a different branch with a separately verified release protocol.

The original decision split into two independent feasibility probes: **C0**, whether the
installed Codex desktop actually launches the opt-in gateway shim for a
submitted WSL New Chat; and **D0**, whether pinned DSH Web's session-controller
mutation seam can be mediated in a disposable Host composition. Failure of
either does not falsify the other. For DSH, a native-session/ACP custom-client
branch is a separately named alternative, not a way to claim Web ownership.
After the D0b probes, the owner selected a **private pinned DSH patch first**
for the lower admission checkpoint. Its candidate implementation is recorded
below; this does not select or activate a full Web profile.

## Review of the previous DAG

The prior DAG usefully separated Codex New Chat, DSH, recovery, safety,
Evolution/UI, website and existing-task handover. This revision changes six
critical dependencies:

1. **Identity before first turn.** Previously active-objective routing could
   develop beside first-turn ingress; P3 now precedes C1/D1/A1, because a
   first message without authenticated ownership can create the wrong durable
   conversation.
2. **DSH Web is not headless DSH.** D0 proves the controller seam before D1;
   A1 is a separately labelled native/ACP client. The existing adapter's
   `dsh-thread-*` replay store cannot silently become a DSH Web journal.
3. **Per-protocol conformance.** P2 preserves Codex, DSH Web and ACP lifecycle
   differences, notably ACK versus completion and journal/cursor recovery.
4. **Read-only can qualify first.** Windows sandbox and effect-enabled release
   remain E0/E1 gates, not blockers for a text-only R1 candidate.
5. **Recovery is client-visible.** C2/D2 need app-visible/history evidence;
   gateway socket delivery alone does not prove consumption.
6. **No forced convergence.** Each surface may be qualified or stopped
   independently. Existing-task handover and website publication remain
   optional branches after their own decisions, not assumed outcomes of new
   chat integration.

The review found no basis to mark C0 or D0 passed from current local tests.

[implementation layering](IMPLEMENTATION-LAYERING.md), and
[New Chat layering](G1-NEW-CHAT-IMPLEMENTATION-LAYERING.md) retain their
historical bounded receipts. This revision is not a replacement for their
