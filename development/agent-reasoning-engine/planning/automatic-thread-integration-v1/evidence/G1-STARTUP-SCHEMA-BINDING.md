# G1 gateway startup schema binding

Status: bounded candidate implementation, 2026-09-26. No current desktop-task
handover, product approval, or activation is claimed.

The Codex gateway now runs `--version` and experimental JSON-schema generation
through its configured command *and* every configured prefix argument before
opening its listener. It compares the version with the profile and pinned host
catalog, then checks byte-level SHA-256 and method ordering for
`ClientRequest`, `ClientNotification`, `ServerNotification`, and
`ServerRequest`. Server method thread-scope groups are also checked. Schema
generation occurs in a private temporary directory removed after the check.
A missing, changed, or invalid schema fails closed; the ready record includes
the verification result on success. DSH startup is unchanged.

The manual catalog verifier uses the same implementation. A direct check
against the selected installed `codex-cli 0.155.0-alpha.16.4` passed with
164 client requests, one client notification, 82 server notifications, and
11 server requests. Six focused startup/verifier tests passed, including a
configured prefix and a same-version schema-drift fixture that exited `4`
before creating its socket. The full serial wrapper test suite exited `0`.
The native user-input canary returned `PASS` with two fixed local provider
requests, zero external model calls, its temporary configuration removed,
and no current desktop-task access.

The Codex gateway CLI also passes its pinned `codex-cli` version into every
new gateway session. Until a live App Server transport answers `initialize`
with a matching version in `InitializeResponse.userAgent`, that session
rejects other host operations. A missing or different reported version
rejects initialization and closes the backend session. Focused tests cover
both acceptance and drift rejection. The native user-input canary now
configures this gate and asserts that initialization completed before it
starts a turn; the pinned installed binary passed with two fixed local
provider requests and no external model calls.
The same gate also passed the gateway-process restart canary: its prior
session resumed, the owned thread rejoined, and an identical request key
replayed without redispatch. Both canaries used a temporary local provider
fixture and did not touch the current desktop task.

## Claim ceiling

This binds startup to the schema generated by the configured command at
preflight time and binds each CLI-started session to the live transport's
*self-reported version*. It does not pin the executable against replacement
between preflight and later process spawn, prove that an already-running
daemon or WebSocket peer uses identical schemas or binary bytes, validate all
payload semantics, or activate ARE control of the current desktop task.
Programmatic gateways need to opt in with `expected_codex_version`; the CLI
configures it. G1 handover and UI work remain separate.

## Open Questions

- Should a later deployment pin the executable digest or process identity
  across preflight and backend spawn to close the remaining replacement race?
- How should daemon-proxy mode prove its running daemon's schema identity,
  beyond its separately checked version?
