The gateway CLI requires an opt-in matching profile and pinned SHA-256 when this desktop mode is selected, resolves and hashes the chosen Codex executable before opening its socket, and starts direct stdio App Server with the same profile flags. Its authenticated connect receipt carries the binary digest and profile for `codex:desktop-wsl`; the client rejects a different or missing binding before accepting input. Private state schema v3 retains the binding across restart and rejects candidate v2 state and drift. ## Claim ceiling and next proof

This is a **plausible next-launch interception seam**. It neither inserts ARE between the already-running desktop client and PID 1954 nor releases that process's writer. It does not prove that a replacement process could safely resume the exact task, that the desktop UI routes every input/approval through ARE, that the account and history watermark match, or that ARE can enforce all effects. No current-task cutover or app restart was attempted.

The next bounded construction is full D2/D3 protocol and lifecycle coverage, followed by a disposable **desktop-owned** task using an isolated WSL command path and startup override, with exact launch, UI ingress, event, shutdown and rollback observations. The managed shim is connected to a candidate gateway client, but exclusive desktop-task ownership remains unproven. Do not substitute this live task or change the user's global WSL `codex` command. Only after those results may the [G1 exact-task gates](../G1-HANDOVER-CANDIDATE.md) be considered; activation remains a separate owner decision under the [session-control contract](../SESSION-CONTROL-CONTRACT.md).

## Open Questions

- Does the installed Windows desktop app inherit a chosen `CODEX_CLI_PATH` on a controlled restart in this package, and can it be scoped to one isolated host rather than every WSL task?
- Can an isolated, authenticated desktop instance open a disposable WSL task through the per-process override without changing the primary app's state? The process-only launch above did not reach that point.
- Does desktop restart close the old writer before the replacement starts and preserve the exact account, task, history watermark, pending UI input and approval routing?
- Can the shim/gateway support the desktop's complete CLI/protocol lifecycle while keeping native effect boundaries non-bypassable and permitting tested reverse rollback?
