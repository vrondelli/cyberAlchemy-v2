# G1 desktop-to-gateway adapter construction

Status: candidate construction contract, not a desktop activation or release. Owner: ARE product and selected Codex desktop host integrator. Scope: the Windows desktop app's version-bound WSL App Server command path, an ARE acknowledged gateway, and the exact task ultimately selected for handover. The TUI is discontinued and is neither a client nor a fallback.

## Why the current shim is insufficient

The [opt-in CLI shim](../../../../implementation/agent-reasoning-engine/packages/codex-app-server-wrapper/bin/are-codex-desktop-shim.mjs) accepts the installed desktop's observed WSL invocation. Its explicit `direct-candidate` mode runs the direct ARE stdio wrapper; the newer `managed-gateway` mode runs a separate acknowledged JSONL client. The standalone direct `initialize` canary establishes command and JSONL compatibility only. An isolated desktop process has not invoked either mode; no UI ingress was observed. See [launch evidence](evidence/G1-DESKTOP-LAUNCH-OVERRIDE-2026-10-01.md).

The [gateway transport](../../../../implementation/agent-reasoning-engine/packages/codex-app-server-wrapper/src/gateway-client.mjs) already offers acknowledged deliveries, a resume-token handshake, adapter binding, and exact gateway faults. Its `runGatewayClientProxy` uses `continuity:false` and remains compatibility-only. The [gateway](../../../../implementation/agent-reasoning-engine/packages/codex-app-server-wrapper/src/gateway.mjs) requires stable request keys for acknowledged mutations and rejects `thread/resume` for a backend thread not previously claimed by that consumer. These protections must be preserved, not bypassed to make the desktop appear connected.

## Target boundary

```text
Codex desktop UI (input, rendering, native account/approval owner)
  -> installed-host WSL command selection (version-bound opt-in shim)
  -> ARE desktop JSONL client (private durable client state and request intents)
  -> authenticated acknowledged ARE gateway (sole bound turn writer)
  -> one declared Codex backend adapter and pinned App Server binary
  -> host model/effect execution under host and user policy

ARE Companion = read-only observation of verified gateway state, not a writer.
```

The desktop adapter must not start a second reasoning controller. It must not silently substitute a new ARE-owned thread for this task. Direct-wrapper and compatibility-proxy modes may remain for development, but must be explicitly named and cannot report an activated desktop session. A missing gateway or failed preflight must stop the managed launch; no direct fallback.

## Non-negotiable state and rollback rules

- A gateway connect receipt is not desktop account attestation, backend history recovery, or current-task ownership. The client must preserve its own durable intent/ack state and compare it with gateway and backend records after restart.
- A client crash after writing a request or delivery can leave the desktop's receipt unknown. Hold subsequent mutations until reconciliation; do not generate a fresh key and redispatch. Fail closed on private-state drift, stale locks, unowned thread IDs, unexpected host method, or capability mismatch.
- No secret, account token, raw transcript, prompt, approval payload, or source path enters launch telemetry or repository evidence. Keep live secrets in a private state root outside the checkout.
- Once a thread has an ARE-owned dynamic effect tool, stopping the gateway does not make direct resume safe; release requires host-confirmed tool removal or rebinding. The current pinned host has not proven that operation.
- Do not alter this task's primary desktop process, global `codex` command, auth home, or installed package as a construction shortcut. Isolated probes remain distinct from G1/O1 activation.

## Validation and evidence gates

Each unit needs negative fixtures as well as a positive path. D1/D2 require a real acknowledged gateway test with a process boundary and an installed-binary canary; a raw stream echo is insufficient. D3 needs durable file recovery, one-writer collision, accepted-but-unknown response and clean restart evidence. D4 requires desktop-side account/writer/ingress proof unavailable from a separate App Server process. D5 requires a rendered desktop journey; a process trace or Companion-only screen cannot stand in for UI input routing. Record the tested host version, binary digest, profile digest, task identity scope, and teardown, with no activation claim from candidate tests.

The opt-in `delivery_handler` and synchronous `connection_handler` transport prerequisites have local socket fixtures: ordered deliveries wait for confirmation before ACK, rejection fails without ACK, and a receipt plus immediate delivery cannot outrun the private resume-token checkpoint. The WSL-only state module persists stable request keys/bindings and gateway deliveries under an exclusive private writer lock. The candidate desktop JSONL entrypoint and managed shim complete `initialize` across a separate client process, actual acknowledged gateway, verified runtime bundle and real ARE wrapper fixture. An isolated canary uses the pinned installed WSL Codex binary and completes the same exchange with no model turn. It exposed and repaired an upstream-ID comparison bug in the gateway's initialize version gate; acknowledged regression tests bind the remapped ID to the original client ID and exact initialization digest and reject a response spoofing the desktop ID. The later D0 hardening requires an explicit gateway `--desktop-host-profile` and `--desktop-backend-sha256`, verifies the selected canonical backend before listening, launches with the observed desktop flags, checks the digest/profile receipt before ingress, and pins that binding in private state. Digest drift and mismatched connect/restart receipts fail closed. The private state schema is now v5 and rejects older candidate records rather than silently migrating them. It additionally checks each owned thread digest against the persisted creation response before accepting the record. Separate authenticated-socket fixtures prove one scoped server-initiated input request and durable reply intent, while unsupported requests and unbound replies fail closed. These checks are not an OS-level executable attestation against path replacement after preflight. None of this proves desktop UI ingress, full protocol/turn lifecycle, or same-task control.

The D2 desktop-output projection keeps ARE-only `cyberalchemy/decision`, `cyberalchemy/successor`, `cyberalchemy/semantic`, and `cyberalchemy/continuity` notifications out of the native desktop delivery sequence. The Codex desktop stream receives only catalog-admitted native messages; equivalent read-only availability of every omitted ARE event for the Companion remains a separate D5 proof obligation. A real gateway and separate client process fixture injects an ARE sideband notice after `initialize` and confirms exactly one native response is checkpointed and delivered. Client socket fixtures reject unknown notifications and malformed/unattributed host requests without output or ACK, and checkpoint an unbound JSON-RPC error before ACK. The installed binary also emits `remoteControl/status/changed` immediately after `initialize`. The gateway now admits this exact version-bound, shape-checked global notification for `codex:desktop-wsl` only on its `interaction-bound` lane, with backend digest/profile and live initialize version bound; fake-backend gateway fixtures reject altered fields and continue to suppress `account/updated`, including outside that lane. The installed-binary base-profile canary delivers the status as the second ordered desktop message. This is not general native global-event parity, desktop account attestation, or same-task control.

The first separate-process turn/approval fixture exposed two integration faults hidden by initialize-only tests. The compiled runtime bundle had admitted an embedded decision profile structurally but not carried a router-verified profile identity into the fixed context provider; every bundled `turn/start` failed as `profile.unverified`. The loader now binds the embedded profile to the matching compiled policy bundle and keeps the verified object identity through context refresh. The desktop state ledger also misclassified an ARE error for a rejected server-initiated approval as an unkeyed client-response; it now admits that diagnostic only after the same server request was delivered and a response intent was journaled, never as a result or unrelated error. The process fixture verifies a file-change approval after an accepted turn, declines `acceptForSession`, then forwards one-use `accept`, with both private intents present before backend receipt. This is candidate D2 evidence, not installed-host approval behavior or desktop UI ingress.

The next D2 slice binds native `serverRequest/resolved` to an observed request ID and owned thread before journaling it. The private desktop ledger refuses a late answer after that resolution; the gateway independently rejects one, and the gateway journal preserves resolved status through compaction. A separate desktop process fixture crosses the actual shim, acknowledged gateway, and ARE wrapper with a fake backend for one turn-bound `item/tool/requestUserInput` and one `mcpServer/elicitation/request` form. It verifies private response intents before backend receipt and ordered native resolution deliveries. See [bounded evidence](evidence/G1-DESKTOP-ELICITATION-RESOLUTION-2026-10-01.md). This does not prove an installed App Server emitted these requests through the desktop route or that desktop UI rendered them.

The subsequent [installed-host MCP canary](evidence/G1-DESKTOP-NATIVE-ELICITATION-2026-10-01.md) closes the fake-only gap for one native form under both observed WSL command profiles, but not the broader D2 completion gate. It exposed a required `experimentalApi` client capability for ARE's generated `additionalContext`. The current installed Windows bundle statically constructs App Server `initialize` with that capability; the canary declares it explicitly. Actual desktop-owned UI ingress and same-task identity remain unobserved.

The same isolated managed path now also has [installed-host user-input evidence](evidence/G1-DESKTOP-NATIVE-USER-INPUT-2026-10-02.md): both command profiles delivered one native `item/tool/requestUserInput`, durably recorded the desktop's answer intent, emitted the matching `serverRequest/resolved`, and completed a local-fixture turn. The MCP mode still passes after the shared canary extension. This is desktop-protocol evidence, not an observation of the installed desktop UI presenting the prompt.

The shared installed-host canary now includes `approval-decline`: a local fixed Responses provider calls the native `exec_command` tool with a requested sandbox escalation and a command that would write only a disposable sentinel. The installed `codex-cli 0.155.0-alpha.16.4` binary (SHA-256 `20694b227d085e4ef69b5042ff7a2b262434eee470ae29f9a8a11b7a7551c520`) emitted `item/commandExecution/requestApproval` through the managed gateway for both `desktop-wsl-base/v1` and `desktop-wsl-app-tools/v1`. The separate test client declined it; the provider saw a denial in the native tool output, `serverRequest/resolved` and `turn/completed` were delivered, the private response intent was present, and the sentinel did not exist. The three focused desktop process tests passed, as did the shared canary's MCP-form and user-input modes after the change. The first two approval-canary attempts failed at fixture prompt routing (`selection.no-match`, then `selection.multiple-capabilities`); the already-used process-fixture prompt `Implement this fixture.` selected the bounded turn and produced the passing runs. This decline-mode result alone did not prove one-use acceptance, broad native approval parity, installed graphical UI presentation, or stock-app New Chat ingress.

The subsequent `approval-once` mode exercises two distinct native command approvals in one pinned-backend turn. For both WSL launch profiles, the first one-use `accept` appended exactly one byte to an isolated scratch sentinel; the installed host then emitted a **second** `item/commandExecution/requestApproval` with a different request ID. The test client declined that request, its disposable command did not run, both request IDs had private response intents and durable `serverRequest/resolved` deliveries, and the provider observed the second denial before the turn completed. The later [native file-change reachability probe](evidence/G1-DESKTOP-NATIVE-FILE-CHANGE-2026-10-03.md) did not obtain a file-change approval. D2's installed-host file-change parity therefore remains open; command approval cannot stand in for it. This says nothing about untested host modes or future binary versions.

The D3 owned-thread checkpoint is a narrower construction slice. The private desktop state records a digest of a newly created thread ID from the gateway-bound `thread/start` or `thread/fork` result before the JSONL client writes that result downstream. It checks that digest before `thread/resume`, fork, turn start/steer/interrupt and compaction; a malformed creation result gets neither desktop output nor gateway ACK. Earlier focused tests passed 19/19; the then-complete wrapper suite passed 756, skipped 24, failed 0 (780 total). A socket fixture verifies queue order and key separation; a separate-process fixture exercises two actual gateway-bound creations and verifies two distinct owned claims. The private ledger separately verifies out-of-order response/key binding, but that is not a claim that the current gateway dispatches concurrent creations. The focused state/client/process suite passed 20/20. Restart after retained deliveries remains fail-closed because a pipe write and gateway ACK do not prove desktop consumption; no clean-restart or installed UI-ingress claim follows from this slice.

The D1/D2 transport now respects socket write backpressure in both hops: gateway input pauses until the socket drains, and the desktop JSONL reader pauses when its gateway input stream fills. A bounded 128-frame socket-stall fixture verifies that ingress pauses and resumes without lost or reordered frames; the gateway-client drain fixture and the separate-process desktop fixtures pass together (15/15 focused tests). The WSL private writer lock now records the Linux process-birth reference as
well as the PID. An orphaned lock can be reclaimed when that PID exists but
belongs to a different process; an uninspectable birth and a live legacy v1
lock remain fail-closed. Focused state tests pass for recycled-PID simulation,
legacy live-PID refusal, and ordinary single-writer behavior. This repairs a
restart lock-liveness edge only. It does not reconcile retained stdout
deliveries, permit a new desktop-owned turn after a crash, or satisfy D4.

A later [read-only private-state diagnostic](evidence/G1-DESKTOP-STATE-INSPECTION-2026-10-02.md)
reports validated, content-free pending-intent and retained-delivery counts
without acquiring the writer lock or changing restart admission. It makes the
D3 refusal inspectable, but does not supply the missing desktop-consumption

The gateway client's framing now uses one streaming UTF-8 decoder across the
connect receipt and subsequent deliveries. A regression splits a multibyte
consumer ID in the handshake and a multibyte message in a delivery across
socket chunks, then verifies the exact message and acknowledgement. The six
focused transport/delivery tests pass in an isolated Linux `/tmp`. This repairs
byte-boundary corruption; it does not establish desktop consumption or D4.
The later inbound-flow slice pauses the socket while a downstream desktop
delivery handler is pending, parses a same-chunk successor only after the first
handler confirms it, and caps retained input at 4 MiB. Focused tests pass
19/19, including ordered ACKs and buffer rejection; the complete wrapper test

The current official [Codex App Server API](https://developers.openai.com/codex/app-server)
documents `thread/read`, `thread/resume`, and turn operations for an App Server
client, but no explicit exclusive-writer release/transfer of an already-open
Codex desktop task is documented there. This is a documentation finding, not
proof that an undocumented host mechanism is impossible. Official
[Codex hooks documentation](https://developers.openai.com/codex/hooks)
describes prompt and local-tool interception, but also documents fail-open
error/timeout paths and tools outside that interception scope. Hooks may be
useful advisory guards; they cannot alone satisfy D4's exclusive-writer and
complete-effect boundary. A separate host-owner contract is still needed.
