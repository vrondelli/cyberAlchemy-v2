# Full-S generation core

Status: offline implemented; 11 synthetic runner tests pass. [runner.mjs](runner.mjs) constructs no client, reads no files or credentials, has no CLI, and imports no evaluator. It is not live-ready. Existing acquisition, qualification and frozen predecessor implementations are unchanged. Open live gates are listed below.

## Inputs and execution

`generationPlan(rows, qualification)` accepts exactly the four fixed source-only rows and an admitted tokenizer qualification. It verifies qualified long-history identity, source/archive digests, complete original-source-order whole-turn chunk coverage, whole-turn chronological-position projection (original position, not date sorting), exact treatment answer messages, AB/BA order and qualification-derived generation reservations. It returns four paired jobs and the qualification digest. Caller-owned source manifest verification and a new freeze must bind the exact rows, qualification and returned plan before effects.

The parent's completed `qualification-r1/RESULTS.json` reports original-history tokens 112,368 / 112,820 / 112,269 / 113,639, chunk counts 36 / 37 / 36 / 36, and treatment inputs 2,795 / 2,720 / 2,768 / 2,682. This implementation task did not rerun qualification. Those counts imply 145 note calls plus eight answers, 153 planned generation calls, 1,131,200 generation reservation tokens, and a separately planned 64,000-token evaluator ceiling (1,195,200 combined). The core derives these values from the supplied qualification; they are not hardcoded and are ceilings, not actual spend or savings evidence.

`runGeneration({plan,meter,generate,record,tokenizer_limits,signal})` runs exactly two pair workers, with sequential calls within each pair. It keeps all four pairs and eight answer slots, including blocked or failed slots. `runPair` is exported for injected tests or a caller-owned schedule with shared health/reservation state; use `runGeneration` for the fixed full schedule.

Control consumes every qualified chunk in original source order, with dates attached and no future question. Each successful 384-output-token note becomes the next request's prior notes. A failed note blocks all dependent notes and the control answer. An ordinary known-cost model failure may leave the independent treatment arm executable; unknown cost, capacity, tokenizer, journal, provider binding or usage-reservation failures stop shared admissions. Treatment consumes only the qualified deterministic projection. Both answer arms use the same adapter answer policy and a 1,024-token output cap. No failed call is retried, no chunk is truncated or repartitioned, and no task is dropped.

## Injected contracts

- `meter(request, {signal})` returns `{input_tokens, wire_sha256}` for the complete immutable future request. Every generation request, including actual carried notes, gets a fresh measurement. Input must be at most 6,976 and input plus reserved output at most 8,000. Planning's 384-note estimate does not admit an oversized actual note request.
- `generate({id,request,signal})` performs exactly one attempt and returns a JSON-compatible receipt with `request_sha256`, `status`, `ok`, `finish_reason`, `output`, and `usage.{prompt_tokens,completion_tokens,total_tokens}`. Only HTTP 200, `stop`, nonempty output, exact wire binding and valid bounded usage complete a call. Completion tokens include reasoning; the core neither discards them nor adds the optional reasoning subtotal again. If reasoning/cached subtotals are present, they must fit inside their parent totals. An exception may carry `receipt`, `usage`, and `model_started:false` only when the transport proves zero model dispatch. Missing usage after entering transport is unknown and holds the full per-call reservation.
- `record(event)` persists independent JSON-compatible `call-start`, `call-result`, `pair-result`, and `generation-result` records without overwriting earlier attempts. It is awaited before dispatch and after responses. It must reject on failed durable persistence. Call records include messages, evidence/request hashes, admission, receipt, output/hash and failure state. These artifacts contain source history and belong in the private benchmark output, not public reports.
- `tokenizer_limits` explicitly declares one shared call cap and deadline across both workers. Tokenizer requests serialize through one queue, while model calls may overlap up to two. Budget exhaustion/timeout stops admissions and retains all slots. The meter receives the combined external/session AbortSignal. Providers and journals must implement their own bounded I/O and honor cancellation; this core does not forcibly terminate noncooperating injected callbacks. The live wrapper must record any unresolved transport/audit drain.

Each ingestion dispatch holds 7,360 tokens and each answer 8,000. Shared and per-pair reservations are checked before every dispatch and are not released for reuse. Known failed-call usage contributes to actual spend. Unknown cost is reported separately as `held_tokens`; it is never silently zeroed. A reported usage overrun remains in observed cost and stops the provider. Generation and pair result persistence failures attach the full in-memory result; an aggregate `usage` shortcut is attached only when all model usage is known. The ledger is an audit record, not a claim that smaller reservation ceilings prove savings.

## Validation

`node --test .../confirmation-v1/runner.test.mjs` passes 11 tests using synthetic rows, meters and providers only. Coverage includes qualified-plan/source mutation rejection, source-order full coverage, carried notes without future-query exposure, identical answer policy, per-dispatch wire measurement, two-worker peak concurrency, eight fixed answers, ordinary failure dependency isolation, unknown/capacity stops, pre-dispatch zero-cost failures, pair/branch persistence receipts, wire/hash and actual-usage failures, reasoning subtotal consistency, shared tokenizer budget and AbortSignal timeout. No real source package, tokenizer/provider endpoint, evaluator reference or network was read/called by these tests.

## Ancestry and remaining gates / open questions

The core follows `../runner.mjs` and `../provider.mjs` failure-accounting semantics and reuses the reviewed local source adapter. It does not modify or implicitly instantiate those ancestor providers. Its injectable exact-wire provider signature intentionally differs from their positional interface; a narrow reviewed shim is still required, including provider request/response digests, no retries, reasoning-inclusive usage, durable receipts, cancellation, bounded secret resolution and HTTP deadlines.

Before generation: independently review this core; bind the verified source-only manifest and qualification; freeze the exact plan and all prompt/transport dependencies; implement a single-use durable output wrapper with 12 GiB host / 8 GiB guest guards, shared health, transport drain, final source/code revalidation and a final error-preserving generation seal; choose and freeze actual tokenizer/elapsed budgets for this much longer trajectory. The core alone provides no effect authorization. No generation freeze or live readiness is claimed here.

Before evaluation: independently verify sealed oracle-reference identity against the S questions, keep those references out of generation, use the blinded native rubric, admit each actual judge wire within 8K, and freeze its separate 64,000-token ceiling. Report fixed-slot completion and actual cumulative model input plus output separately from ceilings and tokenizer work. Are long-depth compact notes sufficient, does retrieval omit necessary evidence, do all actual carry-note wires fit, and is quality/completion preserved with at least 15% measured savings? These remain empirical questions. The candidate has not achieved the benchmark objective.
