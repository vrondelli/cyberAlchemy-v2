# Trusted Input Resolution Implementation Layering

This model separates capability-neutral DomainSpec meaning from provider-neutral integration and the selected SQLite realization. Each layer preserves fail-closed authorization and exact evidence bindings from the earlier Auth vertical.

## Context

- Target: generated trusted-input resolution with a concrete SQLite realization.
- Current state: a handwritten SQLite provider and in-process service pass locally, while generated record-valued result construction is `not_evaluable`.
- Primary operator: Auth Foundation implementation owner.
- Primary constraint: no storage detail may acquire business-meaning authority by proximity.
- Source references: `trusted-input-business-ontology.json`, `trusted-input-source/`, DomainSpec typed-operation contracts, provider-neutral D45-D49 integration profile, and `trusted-input-provider/`.

## Layering Method

- Minimum proof: generate one pure Rust typed Query that returns a provider-supplied snapshot.
- Decision-first: each layer answers one architecture or conformance question.
- Progressive hardening: later layers add neutral integration, concrete SQLite realization, then replayable evidence.
- Non-regression: missing, ambiguous, expired, revoked, incomplete, disabled, or failed resolution continues to yield no authorization authority.
- Evidence-gated promotion: no layer inherits admission, publication, deployment, or production-security authority from technical PASS evidence.

## Layer Boundary Heuristic

```text
Layer value = decision unlocked + user-visible outcome + risk reduced
Layer cost = implementation time + verification time + coordination burden
```

A layer ends when the next unit has lower value-per-cost for its current decision than beginning the next decision layer.

## Layer Decision Table

| Layer | Decision question | Minimum working unit | Operator outcome | Risk reduced | Promotion decision |
| --- | --- | --- | --- | --- | --- |
| L0 | After this layer, we know whether DomainSpec can deterministically construct a record-valued sum result. | Typed payload expression, typed Query closure, generated Rust, tests. | `Resolved(snapshot)` is generated without infrastructure knowledge. | Generator expressiveness and type-safety risk. | Continue only with two-run deterministic generation and negative type tests. |
| L1 | After this layer, we know whether Auth meaning remains complete without storage vocabulary. | Logical identities and a Query/Value Object/Enum/Rule model. | Business ontology and DomainSpec source contain no SQLite row/table concepts. | Infrastructure leakage into product meaning. | Continue only with exact property/variant/rule closure. |
| L2 | After this layer, we know whether SQLite can realize the neutral contracts without contaminating L1. | D45-D49 dependency and persistence bindings, logical-physical mapping, SQLite adapter. | A selected local SQLite realization supplies the generated Query. | Provider coupling and mapping ambiguity. | Continue only with exact adapter/resource/migration bindings. |
| L3 | After this layer, we know whether the complete generated-kernel plus SQLite service is repeatable and fail-closed. | Service composition, mutation matrix, bindings, D65/evidence replay. | Local end-to-end allow/deny behavior is reproducible. | Regression and evidence-inflation risk. | Retain as local candidate; admission and deployment remain separate. |

## Layer Definitions

| Layer | Included scope | Explicitly deferred | Exit evidence | Value/cost notes |
| --- | --- | --- | --- | --- |
| L0 | General payload expressions, root-path payload, typed Query support, Rust tests. | Database reads and Auth-specific logic. | CLI typecheck/tests and two identical instantiations. | Smallest reusable fix for the generator gap. |
| L1 | Logical evidence/binding identities, snapshot, resolution, Rule, Query and relationships. | SQLite tables, columns, indexes, migrations. | Source lint, manifest and typed-closure counts. | Removes authority leakage before binding infrastructure. |
| L2 | Concern-named repository contracts, persistence bindings, mapping reference, SQLite provider. | HTTP, tokens, administration, multi-node storage. | System-integration manifest plus provider tests. | Proves one replaceable infrastructure realization. |
| L3 | Generated kernel invocation, in-process service, fail-closed matrix, D65 chain/evidence. | Admission, publication, deployment and production security. | Two Rust test runs, standalone validator replay and aggregate Auth gate. | Highest-value local closure before external concerns. |

## Non-Regression Guardrails

- Existing Lean claim and historical v1 evidence remain byte-identical.
- DomainSpec never selects SQLite; the project-authored integration binding selects opaque adapter and resource references.
- Duplicate rows remain observable so ambiguity cannot collapse into authority.
- Provider, clock, conversion, migration, or query failures fail closed to public `Deny`.
- Generated code, local PASS evidence, and system ontology candidates do not grant semantic admission or external-effect authority.
