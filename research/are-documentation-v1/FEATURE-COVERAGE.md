# Feature coverage and documentation presentation

## Purpose and scan boundary

Map each of the previous audit's 42 product layers individually to a reader, a page, a presentation form, evidence and a documentation acceptance condition. The scan adds contextual framings as F43 because a source-defined capability was absent from that audit. It also extracts headings and operation-name candidates from 16 top-level package READMEs and lists important subfeatures. This does **not** certify an exhaustive API inventory: exports, every JSON schema field, every CLI flag, internal research scripts and generated ontology records have not all been reconciled. The next completeness gate must enumerate those surfaces and give every public item a page or an explicit internal/excluded disposition.

Current reads include the product profile, release process, supported repository profile, reasoning-state, request-intent, coding-agent and evolution README material, the ACI lineage contract, governance-cutover README and contextual-framing capability/nodes. Existing prior-audit test outcomes are inherited observations, not rerun results. Source existence is checked for each row; README presence is not implementation proof. Package documentation extraction is a discovery index, not a contract or freshness guarantee.

## Online examples and chosen adaptation

[Diátaxis](https://diataxis.fr/) separates tutorials, how-to guides, reference and explanation according to reader need. Use that distinction for ARE pages. A tutorial should produce a bounded successful experience; a reference should specify exact interfaces; an explanation should make the reasoning and limits understandable. Research evidence and proposals need separate labeled collections so an unimplemented idea does not appear as an installation instruction.

[OpenTelemetry's signals documentation](https://opentelemetry.io/docs/concepts/signals/) combines concept navigation with component and language-specific documentation. Adapt this to ARE with a common glossary and reasoning-state concepts, then distinct module, host adapter and model transport pages. The navigation pattern is useful; it does not mean ARE implements an OpenTelemetry exporter.

[Temporal's conceptual introduction](https://docs.temporal.io/evaluate/understanding-temporal) is a useful example of explaining a durable execution model before operational use. Apply that teaching sequence to ARE's ledger, checkpoint and recovery boundaries. Do not borrow Temporal's service guarantees: ARE's single-writer file log is a narrower mechanism.

These are documentation-pattern recommendations inferred from the linked pages, not evidence of ARE runtime behavior. Sources accessed 2026-09-16.

## Navigation and reader journeys

The proposed entry page offers five routes:

1. **Understand ARE:** objective and thesis → definitions → layers → cybernetic feedback model → supported scope and evidence.
2. **Try one bounded workflow:** prerequisites → credential-free routing/context example → inspect a receipt → recover explicit state → optional correction-learning fixture.
3. **Connect an agent:** choose current CLI, Codex gateway, or coding-runtime model transport → exact compatibility → input/output contract → reconnect and error handling. The proposed universal gateway lives in the roadmap until implemented.
4. **Evaluate the research:** hypothesis and falsifier → experiment DAG → protocol and control → metrics/validity/exposure → results and limitations → successor hypothesis. Small-window results link to the actual chapter scope.
5. **Operate or release:** configuration/defaults → state and secrets → diagnostics → test selection → exact closure → candidate lifecycle. Remote service and other platforms appear as scope decisions with prerequisites.

Every module reference links up to its layer and applicable definitions, sideways to its adapters, and down to schemas and executable evidence. Every concept links to one concrete receipt/example. Every roadmap page links to the missing contract or implementation condition, not an invented command. Each thesis should link to implementing feature IDs, counterevidence and the research question that can falsify it; feature presence alone never proves the thesis.

## Status taxonomy

Do not collapse completeness into a single green badge. Each feature carries four independent dimensions:

- **Implementation:** implemented mechanism, candidate/prototype, explicit not-implemented, proposed, or unresolved defect.
- **Integration:** exact host/entrypoint where it runs, injection requirement, isolation and distribution inclusion.
- **Default:** enabled, disabled/opt-in, explicit invocation, selected profile, or not applicable.
- **Evidence:** current source/profile read, dated prior audit, deterministic fixture, controlled live result, held-out outcome, or not evaluated. The inventory uses the first three evidence categories; it does not manufacture fresh runtime results.

Admission, conformance, publication and effect authorization are additional owner decisions and must remain explicit on relevant pages. An inactive low-level verifier flag does not prove a configured cutover is inactive. Current governance-cutover documentation says it verifies the selected admission and activation before composition; successful enforcement still grants no effect authorization.

## Runnable-example rules

Each executable example declares working directory, pinned runtime, exact entrypoint, configuration/profile, dependencies, fixture identity, expected output assertions and cleanup. Mark whether it calls a real provider, requires credentials, changes a disposable fixture, retains disk artifacts, or needs explicit application of a proposal. Prefer a credential-free first example. Placeholder examples are marked illustrative and cannot receive a tested badge.

A tested badge requires a saved invocation, exact source identity, environment, exit status and assertions, and a date. Failure examples must verify the expected error and lack of unintended effects. Validate examples against the documented candidate closure, not an implicitly larger developer checkout. No example should require a personal absolute Node installation path. Do not use live-provider fixtures to imply live-provider qualification.

Test counts describe scope, not quality or completeness: the earlier 914-test receipt has reported discovery omissions. The 411 coding-package count and omitted nested tests must not be blindly added into a new release total without deduplicated suite identities and one reproducible invocation. The 8K GLM release does not establish the full ContextBench acceptance matrix, larger-window completion or transfer to other models/domains; the release README states that limit explicitly.

## Per-feature page template

1. Reader outcome and bounded purpose.
2. Source definition IDs and authority owner; candidate terms stay labeled candidate.
3. Four-part status and supported version/profile.
4. Position in layer/module/adapter graph with typed edges.
5. Input/output schemas, defaults, lifecycle and errors; link complete field reference.
6. One bounded example or explicitly non-executable design sketch.
7. Observable receipt, relevant tests and research evidence; no hidden-chain-of-thought claim.
8. Limits, known failures, unresolved dependencies, retention/cleanup and acceptance condition.
9. Open Questions with owner or owning artifact.

For cybernetic views, name the objective/reference, observer, measured signal, comparator, controller/policy, action gate, actuator and environment. Show feedback separately from forward execution. A dashed proposed edge cannot look like a working integration. Caption what the graph explains and does not prove; link nodes and edges to feature IDs and source evidence. The detailed graph catalog belongs to the architecture pair's output.

## Additional subfeature and module coverage

The 42 audit rows are not an API catalog. The JSON `subfeatures` lists split the largest mechanisms so documentation work does not stop at a package heading. Examples include cache-affinity and observed-token telemetry, portable epoch imports, requirement accounting, repository drift, capability awareness, collect-all preflight diagnostics, research retention currentness, no-gain stopping, evidence-validator injection, sequenced acknowledgements, quotas and signed envelopes.

The JSON `package_doc_scan` maps 16 package READMEs to future `reference/modules/<package>.md` pages and preserves candidate operation names/headings for reconciliation. It includes the small ACI binding package: its current README explicitly implements only intent-route lineage references, not a complete ACI command/dispatch or external conformance. Do not conflate ACI, ACP, MCP or a model's HTTP transport.

Contextual framings adds a source-defined capability beyond the original audit: `CAV2-D67` / `CA2-CAP-GENERATE-CONTEXTUAL-FRAMINGS`. Its 17-node business ontology includes the request, source-bound substrate, distilled knowledge, bounded analogy, candidate, fit assessment, generation workflow and preservation/expiry rules. It explicitly declares runtime implementation absent and measured user outcome absent. It deserves explanation and roadmap pages now, not a working generation tutorial.

A next inventory pass should enumerate every package export, CLI subcommand/flag, public schema definition/field, profile option, adapter contract and capability ID. Join them to these feature IDs and a thesis ID. Any orphan needs either an assigned documentation page or a reviewed internal/excluded classification. That result can support a claim of complete reference coverage; this heading-level design cannot.

## Scope corrections from the audit

The private release unit is a repository candidate, not an npm publication or hosted deployment. HTTP service, tenant isolation, cross-language SDKs, other platforms, MCP and a background research service are optional expansion decisions until their product scope is selected. Their absence is worth documenting but does not by itself block the current private local release. Dependency-closed packaging and complete declared test selection are different: they affect reproducibility of the existing release claims.

The normal gateway is Codex protocol-bound; existing provider-neutral transports belong to the coding-agent layer. Documentation must not promote one into the other. Learning mechanics, enablement, operational provider binding and measured learning benefit also require separate claims.
