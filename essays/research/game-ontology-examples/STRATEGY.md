can inform the BUG-4821 browser escape game. Produce four candidate ontologies,
each showing entities, relations, state transitions, player verbs, evidence
requirements, failure/residue behavior, and implementation consequences. The
result must distinguish observed precedent from synthesis and open questions;
it must not copy proprietary game text or promote any design into product
authority.

## Lanes and groups

### Group `explorers` — parallel, four ontology families

Anti-bias axis: *player agency and evidence structure* (diegetic investigation
vs spatial systems vs interface/meta play vs social/stateful consequence).

1. **Diegetic investigation ontology** — inspect interfaces, reconstruct a
   timeline, and infer from contradictory records. Candidate precedents include
   browser/terminal investigations, detective games, and open-source narrative
   implementations. Return source-backed mechanics and a BUG-4821 mapping.
2. **Spatial systems ontology** — rooms, affordances, physical state, traversal,
   and multi-step environmental puzzles. Search open-source escape-room/3D
   implementations and official design accounts. Return an interaction graph
   that remains playable without hidden pixel hunting.
3. **Meta-interface ontology** — the machine, save/reload boundary, input
   device, or UI becomes part of the fiction. Search documented precedents such
   as controller/input tricks and interface-breaking puzzles, plus safe
   open-source analogues. Return an ethical, browser-compatible version without
   copying protected content.
4. **Social/stateful consequence ontology** — authority, trust, irreversible
   choices, false-green endings, and residue. Search games and repositories where
   the player's evidence or policy decision changes later state. Return a
   bounded state machine and failure semantics.

Each explorer must search both GitHub and non-GitHub sources, record URL,
publisher/author, date accessed, license or rights posture for code, exact
selector/quote anchors (short quotations only), confidence, and an explicit
`observed | synthesis | open-question` label.

### Group `synthesizer` — sequential

Reconcile the four returns into four non-overlapping candidate ontologies. Keep
the same schema across all four and mark conflicts rather than averaging them.
Map each ontology to current BUG-4821 assets, the word-rain gate, three rooms,
and the DomainSpec evidence/authority boundary.

### Group `skeptics` — sequential with feedback capacity 1

Anti-bias axis: *inspiration versus imitation and gameability*. One skeptic
attacks source provenance, licensing, and overclaiming; the other attacks
player comprehension, accessibility, exploitability, and whether a mechanic is
actually fun rather than merely clever. They must predict at least one
disagreement about every ontology.

### Group `writer` — sequential

Write `findings.md` only after evidence closure. Include the four candidate
ontologies, source matrix, rejected precedents, implementation consequences,
and unresolved residue. The strategist separately appends verbatim explorer
returns to `research.md`; the writer must not fabricate explorer quotations.

### Group `auditor` — sequential final approval

Audit source links, selector-level provenance, license boundaries, ontology
completeness, non-authority language, and claim/evidence alignment. Return a
candidate verdict and typed repair requests; do not approve product adoption or
implementation.

## Dependency flow

`explorers → synthesizer → skeptics → writer → auditor` is sequential. A single
`skeptics → explorers` feedback edge may be traversed once when a source gap or
unverified license claim is found. No downstream group runs on an artifact that
has not passed its declared handoff gate.

## Four ontology output contract

Every ontology in `findings.md` must contain:

```text
ontology_id
design_thesis
precedent_set (GitHub + non-GitHub)
entities
relations
player_verbs
state_machine
puzzle_loop
evidence_and_authority_boundary
failure_and_residue
accessibility_and_browser_constraints
BUG-4821 mapping
implementation consequence
open questions
```

The ontologies are candidates for later DomainSpec authoring. They are not
canonical definitions, an admitted system ontology, an implementation plan, or
a release decision.
