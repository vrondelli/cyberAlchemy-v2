Knowledge Expansion Protocol

The evidence-bound protocol beneath CyberAlchemy Exchange, expanding access to encrypted knowledge without erasing its origin.

CyberAlchemy ExchangeDevelopment evidence · 6 Sep 2026Not approved for publication
Contents

Abstract

Digital knowledge can be copied without being surrendered. KEP models that fact as an expansion of an owner set: { A } becomes { A, B }. A remains associated with the artifact while B receives independently controlled access.

The knowledge stays encrypted off-chain. A’s browser encrypts it, B’s browser decrypts it, and Durable Storage retains only ciphertext and sealed recipient envelopes. Solana never encrypts or decrypts knowledge; it records identities, protocol membership, commitments, revisions, and replay protection.

Sharing is represented as a bounded, auditable expansion of access—not an exclusive transfer.
Cryptography and custody

Who encrypts, what is stored, and what Solana proves

Cryptographic ability and protocol authorization are separate. The participants hold the secrets. The hosted service stores sealed material. Solana records which recipient and envelope commitment the protocol recognizes.

A random 32-byte content key encrypts the artifact. The same authenticated ciphertext is shared with every authorized recipient.

Recipient envelopeRFC 9180 HPKE

B’s X25519 public key seals the content key into recipient-specific bytes bound to the artifact, epoch, policy, key binding, and envelope revision.

AuthorizationWallet signature + policy

HPKE Base mode does not authenticate A. A’s signing-key binding, wallet signature, propagation policy, and Solana program checks authorize the grant separately.

This is public-key encryption, not a traditional certificate-authority PKI. The protocol binds a stable Knowledge Identity to a versioned encryption public key. The envelope carries an encrypted content key—not a generic “decryption key.”

Reissue still has a custody requirement.

To create a replacement envelope, A or another policy-authorized fulfiller must be able to recover the existing content key and seal it to B’s replacement public key. The browser trial demonstrates this locally; durable production recovery and custody of that key remain unresolved architecture obligations.

The problem

Files are easy to copy, but proving who authorized access, what exact version was shared, and whether the recipient can still recover it is much harder. Conventional transfer language also suggests that the originator gives something up.

Origin must persist. Adding B must not remove A.

Knowledge must stay private. Neither chain nor service should receive plaintext.

Access needs evidence. A prepared envelope is not releasable until its matching Solana commitment is finalized and reconciled.

Keys will fail. B needs a reissue path that does not create a second grant or alter the owner set.

Implemented vocabulary

Type model

The hosted protocol is not one unstructured record. Its Rust model separates identity, immutable artifact content, prepared intent, recipient material, reissue, and the access projection returned after authorization.

Stable identity. One protocol identifier may survive wallet or encryption-key changes.

Immutable knowledge version. The ciphertext commitment, policy, and encryption epoch identify what was shared.

Revisioned access. Grants and reissues name the revision they expect, preventing stale intent from silently applying later.

Architecture

The browser owns plaintext, the content key, and private encryption keys. The hosted service verifies signed intent, stores ciphertext and sealed envelopes, and observes finality. Solana coordinates recognized protocol membership and commitment revisions but cannot decrypt. SQL-backed durable storage provides the portable record layer; independent backup, restore, and content-key recovery remain production obligations.

Protocol flow

  1. 01
    Establish identity

    A and B bind independently controlled wallets to encryption public keys.

  2. 02
    Seal the artifact

    A encrypts one exact artifact version in the browser and stores only sealed material.

  3. 03
    Prepare and submit

    A prepares B’s envelope, submits the grant, then waits for finalized state.

  4. 04
    Release and decrypt

    The service reconciles matching finalized state, releases only B’s envelope, and B decrypts locally with B’s private key.

  5. 05
    Reissue when recoverable

    B may request a replacement envelope. An authorized fulfiller must recover the unchanged content key; artifact, policy, epoch, and members remain fixed.

  6. 06
    Inspect bounded evidence

    The result proves only the exact state and byte relationships checked by this flow.

Your account, your originals.

The console uses wallet-signed requests and an encrypted account backup. Keep the recovery file privately: wallet access alone cannot restore your encryption keys.

Original files up to 10 MB stay encrypted. The first verified download acknowledgement starts a one-year expiry timer; each later acknowledged download resets it. Before the first, there is no deadline. Extraction remains planned provenance.

What the local tests establish

Recovery restored an identical original. Interrupted saves and download acknowledgements were retried; stale account saves were rejected. A later PostgreSQL repair rejects a second writer and fences writes after connection loss. Browser tests preceded that repair, so a combined run remains due.

Download acknowledgement is not proof of saving to disk. A recovery file is not a payload backup. Lost recovery secrets, independent backup deletion, real wallet compatibility, and live-chain testing remain open. A disconnected service can still return stale reads.
