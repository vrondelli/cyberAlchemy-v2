# Generated AlchLang whole application: Commerce

This directory is a reviewable synthetic `application-v1` application. Its
[`source/commerce.alch`](source/commerce.alch) declares the domain, formal
claims and rules, operations, query, persistence, event and messaging path,
HTTP interface, runtime profile, and two source-authored Realizations.
[`source/commerce.alch.application.json`](source/commerce.alch.application.json)
binds the exact companion inputs. `generated/` is produced by the public
AlchLang `check`, `build`, and `verify` path, not hand-written application code.
The authored `FindOrder` Query remains a separate declaration; `SubmitOrder`
uses a keyed Entity read so eligibility is checked for the requested identity.

The separate [payment-outbox candidate](candidate/payment-outbox.alch) uses
AlchLang's first-class Money, Currency, PaymentStatus, Event, and State Machine
declarations. It is not part of this generated application's source manifest;
the [candidate contract](PAYMENT-OUTBOX-CONTRACT.md) records the post-commit
authorization behavior and the unimplemented joins.

From this directory, run:

```bash
node test.mjs
```

The test checks source and generated bytes, executes the generated submission
handler with missing, matching, and cross-identity keyed reads, runs a signed HTTP
request through the generated adapter and application runtime into that
handler, type-checks and compiles the generated TypeScript application in a
disposable copy, tests its signed HTTP adapter independently, rejects a
tampered graph in that copy, and
verifies the retained original again. It also checks that the generic reference
store rejects a nonempty write batch and that an unimplemented outbox drain
fails explicitly. The generated outbound adapter requires a valid idempotency
key before any HTTP call. It requires the checkout's locked Node
toolchain and local development dependencies; it uses no live database,
broker, credentials, external provider, or deployment.

Suggested inspection order:

1. `source/commerce.alch` — authored application and Realizations.
2. `generated/.domainspec/application-graph.json` — whole-application joins.
3. `generated/src/integrations/application-request-handlers.ts` and
   `generated/src/features/commerce/application/operations/` — generated
   business path.
4. `generated/src/providers/reference/` — generated provider adapters, with
   state writes and outbox drain still deliberately unimplemented.
5. `generated/.alch/manifest.json` and `.alch/whole/` — artifact and runtime
   binding evidence.

`runtime_guarantees_observed` remains false: the scenarios establish only the
named local observations. This is not proof of live PostgreSQL, NATS, outbound
delivery, business completion, production behavior, or product approval.

## Call it over REST in Docker

The Docker image compiles the **generated** TypeScript application. The generated
inbound adapter now carries the authored `POST /orders` path, while a separate
[`docker/server.mjs`](docker/server.mjs) supplies a review-only in-memory store
and exposes that route through the generated
`GeneratedApplicationRuntime`. Its signature check reuses generated code.
The generated PostgreSQL reference adapter is not used: it currently does not
implement the keyed read/write behavior needed for this business flow. The REST
`GET /orders/7` and the in-memory store are review scaffolding, not
compiler-generated or durable-provider guarantees.

From this directory, with Docker Compose, Node, and OpenSSL available:

```bash
export REVIEW_WEBHOOK_SECRET="$(openssl rand -hex 32)"
docker compose -p alchlang-commerce-review up --build -d
curl http://127.0.0.1:8080/health
node docker/smoke.mjs
```

`compose.yaml` publishes only to `127.0.0.1` on the host. If port 8080 is
occupied, set `REVIEW_PORT` before starting and set `REVIEW_BASE_URL` to the
matching URL for the smoke test. The container requires the secret at startup;
do not put a real credential in the repository.

To call the REST endpoint yourself:

```bash
BODY='{"id":"7","accepted":true}'
SIGNATURE="$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$REVIEW_WEBHOOK_SECRET" -hex | awk '{print $2}')"
curl -i http://127.0.0.1:8080/orders \
  -H 'Content-Type: application/json' \
  -H "x-domainspec-signature: $SIGNATURE" \
  --data-binary "$BODY"
curl http://127.0.0.1:8080/orders/7
```

Expected: the signed request returns `200` and
`{"id":"7","accepted":true}`; no or wrong signature returns `401`. The
review store starts with only order `7`, and only that ID is accepted. State
exists only in this container process and resets on restart. To stop and
remove this exact Compose project:

```bash
docker compose -p alchlang-commerce-review down
```

The local image and `node test.mjs` offer inspection and bounded tests. They
do not claim a production-ready API, persistence, authorization, scalability,
or public network exposure.
