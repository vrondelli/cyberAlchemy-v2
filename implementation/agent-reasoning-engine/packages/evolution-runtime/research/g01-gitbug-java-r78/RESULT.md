A source-only inspection of the parsed failing-test message/stdout/stderr

equivalent to isolated test stderr and has not been admitted for a prompt.
Thus a proposed stack-frame-only retrieval method is not yet a credible
universal treatment. R77's exposed Bears loss included a misleading GLM
summary that demoted a file already ranked second by both raw retrieval
arms; any next method must control this failure mode and be compared against
a strong matched baseline.

## Exposed development, r80–r91 — 2026-10-05

R80 prospectively partitioned the 53 source-order repositories: ordinals
1–12 for exposed development, 13–36 as the intended 24-case confirmation
block, and 37–53 as source-order replacements only for predeclared
eligibility failures. All **12/12** development exact buggy archives passed
the fixed 128 MiB compressed, 512 MiB declared, and 64 MiB projected Java
caps. R81 sealed 12 failure-side-only 1,024-byte queries before R82's
evaluator-only old-side Java patch audit, which admitted **12/12**.
R83 obtained complete ARE rankings over 12 isolated failed-source indexes.
No confirmation labels or rankings were opened.

R84–r85 tested a deterministic failing-test-class symbol channel. Against
ARE+raw-BM25, the source-only safeguarded three-channel treatment improved
development MRR@8 **0.2917→0.4036** over all Java files. A stronger
raw-BM25+symbol comparator scored **0.3854**. Because GitBug-Java here is
`SOURCE_ONLY`, a common production-file filter was also evaluated in
development: ARE+raw-BM25 **0.4708**, raw-BM25+symbol **0.6119**, and
the safeguarded treatment **0.6972**. The latter exceeded the stronger
comparator on only **2/12** cases (10 ties), with one large win driving most
of the aggregate. This filter was chosen *after* development exposure; it
cannot be projected backward as a frozen confirmation rule.

R86 made exactly 12 private VPS GLM tokenizer and 12 generation calls from
the sealed development queries; all 12 summaries were valid. Provider
usage reported 2,761 prompt and 535 completion tokens. The VPS run root
`/opt/are-benchmark-runs/g01-gitbug-dev-r86` was cold-copied to WSL, and
the sorted file-hash digest matched on both sides:
`0e370b8bd2ffd26e8684756b3bad32105a8a75c27704941f23d7e091c8f4eca1`.
R87–r89 found that the additional functionality channel barely changed the
production-filtered development result: safeguarded four-channel MRR@8
**0.7000** versus no-GLM **0.6972**. This does not justify a paid GLM
channel in a fresh claim run. Its summaries and full provider payloads
remain private.

The unchanged symbol rule was then replayed on the **already exposed**
24-repository Bears Java cohort, with source rankings sealed before
evaluator access (r88). Under the same production-file filter, ARE+raw-BM25
scored **0.5945** MRR@8, while the safeguarded symbol treatment scored
**0.5570**. The transfer hypothesis failed; GitBug development performance
cannot justify using the untouched GitBug block for this rule.

R90–r91 tested a no-model compact Java declaration representation
(path, package, types, and method-shaped names), motivated by the primary
[retrieval-oriented code representations study](https://arxiv.org/abs/2607.11046).
With the common production filter, GitBug development scored **0.6306**
for raw+symbol+structure, **0.7000** for the safeguarded ARE treatment,
but the latter won on only **1/12** cases. On exposed Bears, the same
matched structural comparator scored **0.5441** and treatment **0.5883**,
yet simpler ARE+raw-BM25 remained higher at **0.5945**. This regex-based
representation did not establish a robust cross-population advantage.
Neither the GitBug nor Bears exposed score is a superiority claim.

The GitBug and Bears source seals were written before the [r97 evaluator](audit_test_usage_r97.py)

in 4/12 cases, produced candidates in 3/12, and reached gold in **1/12**
top-three/top-ten lists. Bears resolved a method in 6/24 cases, produced
candidates in 4/24, and reached gold in **3/24** top-three/top-ten lists.
The evaluator receipts are SHA-256
`859a5f8e5c0aa82a6f91d2470463a428e5489a53f3333b10762c36f2716ade13`
and `21896db851ff16a5fe6400adb31e03e2af05893d9ad6b35d1c60d00c2c784581`.

A bounded read-only source diagnosis found 19 distinct GitBug and 30 Bears
failing test-class/method references in the sealed queries. The buggy source

`shouldThrowForMalformedPropertyPath` method does not. The principal
limitation is therefore missing method source, not merely weak Java parsing.
Do not promote this rule or spend the untouched confirmation block on it.
