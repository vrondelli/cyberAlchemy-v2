It reads only question text, the 200 small-tier trajectories, the r2 line index, and prior packet wires; it does not read gold or confirmation question fields. It replays every original r2 lexical selection before changing treatment. It preserves every r3 control packet and the specialized item-form treatment. ## Audited development result

The [r8 final scorer](../research/g03-beam-r1/score-lme-v2-dev-site-final-r8.py) independently verified every new tokenizer, answer, and judge raw receipt hash and used the official binary-judgment parser. It resolved new judgment arms only when both votes agreed. Site-scoped treatment is **7–9/28** versus unchanged control **3–4/28**; prior treatment was **6–8/28**. The control and 18 unchanged treatment answers are inherited from the earlier r5 run because their frozen request evidence is identical, so this is a development delta comparison, not a newly contemporaneous 56-call paired campaign. On 25 fully resolved pairs, there are 3 both-correct, 4 treatment-only, 0 control-only, and 18 both-wrong, for two-sided exact McNemar **p=0.125**. The sole new correct case is Magento admin tracking-number navigation `8957a127`; no changed case lost a previously correct resolved score. The private final score SHA-256 is `05579acd67ba8d525de190215aa0384197b9b18d33a827722e071895a952993d` at `/home/vlad_/are-benchmark-archive/g03-lme-v2-dev-site-judge-run-r8/SCORE.json`.

This is a small development gain, not substantial improvement or superiority. It is a custom matched GLM reader with GLM-adapted judgments, not the official LongMemEval-V2 backend/reader/latency protocol. The site mapping used exposed source inspection; the same 28 questions were previously scored; three inherited judge arms remain split; and absolute accuracy remains low. No product-page headline or held-out confirmation dispatch follows.

For the ten changed answer calls, known reader prompt tokens fell **11,675 → 10,297**, but known completion tokens rose **991 → 2,741** because one new answer exhausted the 2,048-token cap. Total known answer tokens therefore rose **12,666 → 13,038**; this is not a demonstrated efficiency gain. These figures exclude judge and retrieval compute, and they do not substitute for the official online memory-query latency metric.

## Next research boundary

The [official AgentRunbook-R baseline](https://github.com/xiaowu0162/LongMemEval-V2/blob/main/memory_modules/agentrunbook_r.py) indexes raw state slices, transition events, and procedure/hint notes, and generates multiple retrieval queries. Our six-line-window FTS cannot represent full page state or absence and misses relevant workflow transitions even when the correct trajectory is present. A next candidate should index source states and action transitions, retrieve exact quoted UI anchors plus site-scoped states, and render bounded before/after page evidence under the same 8K reader ceiling. First test evidence reach and token qualification on the exposed 28 questions; only then spend more answer calls. Do not silently add labels or question-type metadata to retrieval, change prior receipts, or open confirmation because site contamination reached zero.
