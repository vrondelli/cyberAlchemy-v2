# G01 r15 development-pool screen — candidate protocol

Status: predeclared private preparation, not a frozen or dispatched campaign.

## Objective and boundary

Test whether the pinned ContextBench development partition can provide an
independent 24-task G01 successor after r14, using the prospectively qualified
r46 source. The r14 cohort is terminal; its 24 selected IDs are conservatively
exposed. The original 233 reserved-confirmation IDs remain excluded.

The post-r14 receipt join leaves 21 known-clean unused development tasks.
Only 12 slots remain under the old three-per-origin cap; even if every remaining
unscreened task were clean, that cap permits at most 15 fresh slots. A new
24-task campaign therefore cannot inherit r14's population protocol. This
screen tests a separately declared maximum of eight tasks per Git origin.
Under that cap, the current known-clean supply yields 20 slots, and the
source-valid upper bound is 40. These are feasibility counts, not quality
estimates. A later cohort selection must be score-blind and separately frozen.

## Fixed screen

Use only the eight source fields used by r14, the same pinned 1,136-row Parquet,
and its 903/233 development/reserved partition. Exclude all manifested G01/G02
IDs, both r13 selected cohorts, all 67 r14 screened IDs, and all 24 r14 selected
IDs before drawing. The selection tool checks pinned input hashes and refuses
output overwrite. Draw eight unscreened source-valid Python tasks from each of
Ansible, Django, Transformers, and Sympy. Within each origin, sort by SHA-256
of the fixed seed and instance ID, then by ID. No label, gold path, native
score, model output, or benchmark result enters selection.

Only after sealing the source-only manifest may the evaluator-only exact-base
gold-lineage rule screen those 32 IDs. Export eligibility bits and aggregate
counts, never gold file paths or content. No GLM call or ARE read is part of
this screen. If enough clean slots exist, a *new* source-only 24-task candidate,
native-reference/cache/index/storage preflights, provider check, definition,
and freeze are still required before dispatch. If not, do not top up this draw
silently; define a separately named screen or different population.

The eight-per-origin and likely four-/five-origin population is development-
only and less diverse than r14's 13 origins. Any eventual result can support
only its exact cohort/date/protocol claim, not full ContextBench or general
ARE superiority. The original reserved-confirmation partition is not reused.

## Construction and operations

Product frontier: qualify a prospective correction for the exposed r15
read-delivery failure, then select and freeze a fresh, unexposed cohort.
Runnable work: transfer-test source-verified late binding on exposed cases,
check new clean-label supply, bind a new source tree and strict claim rule,
then run a separately named matched campaign.
Operational prerequisites: retain the exact VPS source caches, overlay views,
and private receipts; the owner is the private benchmark operator. Causal
blockers: the r15 24/24 gate failed and a successor has not been qualified or
frozen. Deferred residue: external fresh
confirmation population, full campaign reliability, and Vlad/Dave product-card
review.
