# G02 file availability versus final selection — exposed diagnostic

Status: private, read-only development analysis on the already exposed G02 r2 and r3 scored pairs. This is **not** a new model run, a candidate result, or superiority evidence. Original predictions, scores, and receipts were not changed.

The diagnostic compared each original ARE and DSH `native-score.json` with the existing sealed all-delivered-read diagnostic for the same pair. A correct file appearing anywhere in the ARE delivered-read union but absent from its final selection is *available yet unselected*; a correct file absent from that union requires acquisition or another observation mechanism. The union is an availability probe only: adding it wholesale can introduce many false-positive files and has already failed as a general F1 strategy.

| Exposed scored cohort | ARE File-F1 lower / higher / tied vs DSH | Lower-F1 cases with fewer correct selected files | Of those, additional correct file already delivered / not delivered | All scored cases with an additional correct file delivered but unselected |
| --- | ---: | ---: | ---: | ---: |
| r2, 23 valid pairs | 16 / 4 / 3 | 10 | 6 / 4 | 14 / 23 |
| r3, 9 valid pairs | 5 / 2 / 2 | 2 | 1 / 1 | 2 / 9 |

In the remaining File-F1 losses, ARE generally selected the same number of correct files but more total files: five r2 cases and three r3 cases. One r2 loss has a more complex precision/recall tradeoff and should not be forced into either simple category. These counts are descriptive of exposed cohorts; the r2 23/24 and r3 9/12 validity denominators remain unchanged. They are not statistically independent tests of a new hypothesis.

Implication: a prospective G02 candidate needs (1) precision-protecting selection among **receipt-bound** reads already acquired and (2) a separately bounded, source-only acquisition path for genuinely missing files. Both must use task/source signals rather than native gold, preserve the delivered-read contract, and be evaluated on exposed losses *and* prior wins across repositories before freezing any untouched matched-arm holdout. No per-task gold-derived rule, post-hoc score transformation, indiscriminate read union, or r2/r3 reuse can support a superiority claim.

## File-mention and read-frequency probe

The [read-only diagnostic script](../research/g02-product-r4/diagnose-file-mentions-r1.py) (SHA-256 `9a92c838ee23e0652fd8d81b842970c90219fc6a9ed00f38b44c37bdccc179c4`) was streamed to `python3 -` on the VPS; it wrote no remote files and made no model calls. It rechecked all 23 scored r2 and nine scored r3 pairs against the pinned evaluator's gold, aggregating counts only. Gold was used solely for this offline analysis, never as a runtime feature.

Across the 32 pairs, original ARE final selections contained 112 correct and 51 incorrect file selections; delivered-but-unselected reads contained 25 correct and 239 incorrect files. The issue text explicitly named **none** of those 25 unselected correct files, by full path or exact basename. Literal issue-filename matching therefore cannot rescue this omission class. Selected correct files had a median of three delivered reads and 74.5 cumulative read lines, versus two reads and 44 lines for selected incorrect files. Yet a one-read pruning rule would remove 20 correct along with 23 incorrect selections; frequency alone is not a safe precision fix. Among delivered-but-unselected files, requiring at least three reads retains only seven correct and 26 incorrect files (from 25 and 239). This enriches the correct-file fraction but is far too imprecise to justify indiscriminate promotion. These are pooled, exposed, exploratory counts; repeated files across tasks are counted per pair and no transformed predictions were scored.

The actionable next mechanism is a task-conditional evidence-relevance decision over delivered reads, with explicit protection for previously successful cases, plus a bounded source-acquisition rule. Mere filename mention, read volume, or read frequency has insufficient separation in this population. Any chosen rule still needs a separately versioned prospective implementation and fresh matched-arm validation.

The subsequent [lexical evidence probe](../research/g02-product-r4/diagnose-lexical-evidence-r1.py) (corrected SHA-256 `ebb22740b73bbc3deb109047522e1c75aff6db99be52b9b3f75f4d3142c48d4f`) tokenized issue text and the source ranges already delivered to ARE, then ranked file-level issue-word overlap with within-task inverse-document-frequency weights. A preflight caught that its first pass had read the post-run `sources/session/work` tree, not the pinned `sources/session/base` tree; those first-pass counts were discarded. The corrected read-only base-snapshot run made no model calls, prediction edits, scoring, or new cohort exposure. Across the same 32 exposed scored pairs, the top unselected file was uniquely correct in only **6** tasks and uniquely incorrect in **26**. The selected correct-file lexical score was higher on average than selected incorrect-file score, but a simple within-task rule that prunes a unique lowest-scoring selected file when its score is under half the highest would remove **17 correct** and only **9 incorrect** selections. This rejects direct lexical promotion and pruning as safe general G02 fixes. The ranking is a diagnostic, not a candidate chosen for a holdout; its source ranges and gold judgments remained separate.

A [no-model reviewer-packet preflight](../research/g02-product-r4/preflight-receipt-review-r1.py) (current SHA-256 `69f614b67db9181c48772961082157184250bec8f8453f241d7e865777319cd5`) then validated all 32 exposed scored pairs against the pinned base tree. Each checkout's Git HEAD matches the prediction commit and has no tracked changes; every selected final span has an exact delivered read; every included range is in bounds; and a packet containing the issue, current selected paths, and all delivered range handles fits below 55 KiB (median 35,501 bytes; at most 72 handles and 35 files). This establishes *technical feasibility* for a separate bounded reviewer using only receipt-bound reads, not its accuracy, cost, or eligibility for a new holdout. Any reviewer must be versioned, frozen before scoring, and tested on exposed wins and losses without access to gold.
