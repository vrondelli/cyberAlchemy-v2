# Property-to-Repair Assurance Expansion Plan

Status: planning candidate. Complexity: high. Authority effect: none.

## Objective

Prove that the completed property-to-repair workflow can resist selected
false-success paths, evaluate the existing three-replica CRABS experiment, and
transfer to a financial-settlement rule before packaging a bounded service
candidate.

Success is a chain of earned decisions:

```text
completed reference case
  -> trustworthy 48-case evidence mechanism
  -> complete typed 48/48/2 outcome
  -> negative controls detected
  -> independent replay
  -> owner-confirmed financial property
  -> second-target replay
  -> measured service candidate
```

The workflow does not promise that a natural defect will be found. Valid
outcomes remain counterexample, no counterexample within bounds, inconclusive,
or conflicting evidence. Repair is conditional on a confirmed defect and an
exact change scope.

## Fixed decisions

1. The completed two-singleton CRABS package is immutable inherited evidence.
2. The existing partial-knowledge experiment retains 48 native cases, the same
   48 sanitizer cases, and two actual-C CBMC representatives.
3. Its [implementation repair plan](../crabs-partial-knowledge-move-candidate-v1/implementation-repair-plan.md)
   owns R00-R09 implementation detail. This plan sequences and gates that work.
4. Owner decision: Task Session is excluded. T0 removes the legacy hardcoded
   gate and derives readiness from current code, tests and technical preflight.
   Exact owner authorization governs each native execution scope.
5. Negative controls run against isolated successor copies or explicit mutation
   adapters. They never rewrite the frozen accepted subject or prior evidence.
6. Financial settlement is the proposed L3 target. Its current C3/P4 evidence
   and eight mutations are candidate inputs, not owner approval or full coverage.
7. Service packaging uses measured effort and outcomes from L2/L3. It creates
   no price commitment, customer claim or external communication.

## Negative-control contract

The L2 campaign must select at least one control from each class:

| Class | Required examples | Required result |
| --- | --- | --- |
| Subject repair | restore destination-tail placement; omit placement metadata; reject a valid merge | The affected declared property becomes counterexample or explicit non-pass. |
| Oracle/harness | weaken order comparison; omit merge-success/member checks; change selected assertion | Freeze/comparison validation rejects the changed assessment. |
| Denominator | omit or duplicate a case; cross-run row; wrong case ID | Completeness/provenance check rejects success. |
| Evidence | stale source/tool binding; tampered raw output; contradictory normalized result | Receipt validation rejects or reports conflict. |
| Execution | launch failure; timeout after pipe EOF; output overflow; interruption and recovery | Truthful terminal state, bounded cleanup and no false pass. |

The exact mutation matrix is frozen before execution. Unexpected surviving
controls block L2 promotion and remain evidence; controls are not silently
removed to obtain a pass.

## Financial-settlement transfer contract

Node K presents the current C3 deal-split rule and P4 payout-effects rule to the
domain owner with their four cases, eight detected mutations and unresolved
clauses. The owner selects one property, rejects both, or requests a bounded
revision. Only a selected property advances.

For the selected property:

- state whether it is TDE-derived, manually authored or adopted from existing
  experimental evidence;
- bind exact source, generated adapter, production-facing consumer, fixtures,
  proof context and validation tool;
- preserve positive cases so a reject-all implementation cannot pass;
- run a bounded counterexample search and existing mutation calibration;
- construct a repair only if a real defect is confirmed and its exact mutation
  scope is separately authorized;
- perform independent replay using the common evidence contract and record
  adapter-specific work separately from reusable-core work.

## Failure and rework

Provider failure, timeout, missing rows, stale bindings and disagreement are
typed results. They do not satisfy a success gate. A repair or contract change
creates a successor freeze and fresh downstream evidence. Previous attempts and
review findings remain immutable.

If current code already implements part of R00-R09, T0 records exact passing
evidence and plans only the remaining gap. It does not mark work complete from
labels or historical intent. If the 48-case subject exposes a defect, pause
promotion, explain and bound it, then route any repair separately. If neither
financial property receives owner confirmation, L3 stops without replacing it
with an inferred property.
