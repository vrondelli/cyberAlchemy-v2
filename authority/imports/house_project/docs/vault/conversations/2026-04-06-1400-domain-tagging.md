# Domain Tagging System Design

**Date:** 2026-04-06 14:00 (UTC-3)  
**Tags:** #ontology #domain-tagging #vault-integration #architecture

## Summary

This session designed and partially implemented a code-to-domain bridge system using Python `@biz` docstring tags, addressing the problem of establishing semantic links from code to business vocabulary. The goal was to make it easy for agents and humans to ask "where is X term used in code?" without manually maintaining an external registry.

### Core Design Decisions

**Tag mechanics:**
- Tags live in docstrings (coupled to symbols), not external comments — this keeps the tag definition and the code it annotates physically together.
- Schema is minimal: only `term` and `type` fields — simplicity enables quick adoption.
- Taxonomy types derive from domainspec: entity, value-object, operation, query, rule, calculation, workflow, state-machine (8 primary types, though fuller taxonomy may expand).
- Code is the source of truth; an external registry is generated by scanning, never hand-written or manually maintained.

**Dictionary integration:**
- Dictionary entries now carry `Taxonomy type:` and `Edges:` fields, creating a bidirectional link between business concepts and code.
- Dictionary is intentionally a superset of taggable code — not every term must have code, but every tag must match a dictionary entry.
- Tags implicitly carry relationship edges via the taxonomy type (e.g., a `rule` enforces an `operation`, no explicit edge declaration needed in the tag).

**Adoption strategy:**
- Tag on demand when editing business-relevant code — no big-bang backfill.
- When a function resists tagging under existing terms, the solution is often to add a missing dictionary term, not to allow multiple tags.
- Example: `cross_check_fields` was difficult to categorize until **CrossCheck** was added as a new Rules & Validation term with proper definition and aliases.

### Key Insights

**Complementary systems:**
- @biz tags map the **code→domain direction** (code to business meaning).
- Vault-code-bridge (existing discovery) maps the **vault→code direction** (vault to code implementation).
- These are complementary, not competing — together they provide full bidirectional navigation.

**Technical vs semantic navigation:**
- GitNexus maps execution flow (technical: "what calls what").
- @biz tags map business meaning (semantic: "what term does this implement").
- Together, they cover the full navigation need.

**Edge inference from taxonomy:**
- Taxonomy types implicitly carry relationship semantics. A `rule` enforces an `operation` under the same term. No explicit edge declaration is needed in the tag; edges are derivable from the taxonomy structure.
- Edges in dictionary entries are declared bidirectionally to maximize local information (e.g., EligibilityFilter declares `produces → FilterResult` AND FilterResult declares `produced-by ← EligibilityFilter`).

**Dictionary as missing-term detector:**
- When a function has unclear tagging, the question is not "allow multiple tags" but "is the dictionary missing a concept?"
- Many apparent multi-term cases (functions serving multiple domains) turn out to be missing vocabulary once examined carefully.
- This insight partially resolves Open Question 3 (multi-term symbols) by shifting the problem from code to the dictionary, where it is more tractable.

### Formal Output: Domain-Tagging Constitution

A new constitution was created at `specs/ontology/docs/possible_constitutions/domain-tagging-constitution.md` with 14 numbered rules covering:

1. Tag placement and format (docstrings only, specific syntax)
2. Schema constraints (term, type fields only — no table, event fields)
3. Dictionary dependency (every tag must match a dictionary entry)
4. Taxonomy type catalog (the 8 primary types and their definitions)
5. Edge inference rules (how taxonomy implies relationships)
6. Missing term discovery (when to add to dictionary vs. multi-tagging)
7. Tag-on-edit adoption (no forced backfill, no registry hand-written)
8. Infrastructure exclusion (utilities, services outside domain logic are not tagged)
9. Reserved types and anti-patterns
10. Agent notes for tagging decisions
11. Review checklist for new terms
12. Governance for updating the constitution
13. Multi-term rationale and resolution heuristics
14. Examples with real code symbols

This constitution is modeled after `event-system-constitution.md` — numbered rules, clear anti-patterns, agent decision trees, and formal governance.

### Real @biz Tags Added to Code

Six symbols received initial @biz tags to validate the system:

```python
# domains/aquisicao/use_cases/
class EligibilityFilter(ABC):
    """@biz: EligibilityFilter | type: rule
    Abstract base for acquisition eligibility rules."""

class ConcentracaoMaxFilter(EligibilityFilter):
    """@biz: EligibilityFilter | type: rule
    Enforces max concentration on a single operation."""

# domains/shared_services/documents_validation/
class FilterResult(Enum):
    """@biz: FilterResult | type: enum
    Enumeration of possible filter outcomes."""

class FilterOutcome(NamedTuple):
    """@biz: FilterResult | type: value-object
    Dataclass carrying filter result details."""

def cross_check_fields(...):
    """@biz: CrossCheck | type: rule
    Validates OCR-extracted fields against database rows."""

class CrossCheckResult(NamedTuple):
    """@biz: CrossCheck | type: value-object
    Result of a cross-check validation."""
```

These tags demonstrate:
- The same dictionary term (FilterResult) can have multiple taxonomy types across different code symbols (enum and value-object).
- Tags work well when backed by proper dictionary entries (all 6 above have entries in `dictionary-business.md`).
- The tag schema is minimal and does not burden the docstring.

## Epistemic Impact

### Foundational Beliefs Validated
- **`ontology-premises.md` (assumed):** If a premise exists that code-to-domain mapping is viable, this session validates that domain tagging is a practical, low-friction approach complementary to vault-code-bridge.
- **Dictionary as superset principle:** The session confirms that it is acceptable (and even preferable) for the dictionary to be a superset of tagged code. Not every business concept needs a code counterpart, but every code tag must reference a dictionary term.

### New Premises Established (Candidate for Promotion)
- "When code resists tagging under existing terms, the solution is often a missing dictionary entry, not allowing multiple tags on a single function."
- "Dictionary entries should carry taxonomy type and edges as structural metadata, not just definitions."

### Spec Drift Discovered
- **`vault-code-bridge discovery doc`:** Claims 13 taxonomy types, but the refined decision is to use 8 primary types. The fuller catalog may be referenced but not enforced in tags. Spec needs clarification.
- **`aquisicao-tag-plan initial version`:** Had incorrect claims about which symbols were already tagged and which terms were in the dictionary. Corrected during review pass (see Gaps & Backlog section below).

### Dictionary Structure Updated
- Added `Taxonomy type:` field to dictionary entries (e.g., "Taxonomy type: rule", "Taxonomy type: enum").
- Added `Edges:` field showing related terms and relationships (e.g., "produces → FilterResult", "produced-by ← EligibilityFilter").
- Pattern established with EligibilityFilter, FilterResult, and CrossCheck entries.

## Open Questions

1. **Registry format and location:** Should the generated registry be YAML, Markdown, or both? Should it live in `docs/vault/` or as an external artifact? This decision gates the registry generation script.

2. **Multi-term edge cases:** Some functions may legitimately serve multiple unrelated business domains (not just a missing dictionary term). Should these functions be allowed multiple `@biz` tags, or should they remain untagged? Example: a utility function used by both aquisicao and liquidacao (if such exists). The constitution assumes "missing term" resolution, but edge cases need team consensus.

3. **Tag-on-edit adoption timeline:** When should the first big push for backfilling tags occur? After the constitution is ratified? After the registry generation script is ready? The tag-on-edit strategy is low-friction but may leave large parts of the codebase untagged for months.

4. **Dictionary term lifecycle:** Once a dictionary term has `@biz` tags pointing to it, is it "locked" from deletion or major redefinition? How do we handle dictionary term deprecation when code depends on it via tags?
