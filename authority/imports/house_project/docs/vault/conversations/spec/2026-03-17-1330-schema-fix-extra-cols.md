# Fixing Missing Complementary Columns in Aquisição

**Date:** 2026-03-17 13:30 (UTC-3)
**Tags:** #migrations #aquisicao #models #extra-cols

## Summary
This session focused on investigating and resolving an issue where the `complementary_data` JSON column (among others) was missing from the `aquisicao_manual` and `aquisicao_manual_staging` tables in the database, despite being defined in `models.py`. The root cause was traced back to a tangled migration state resulting from a previous multi-tenancy rollback that left partial schema changes (tables like `aquisicao_extra_cols` and renamed `cadastro_emissor` columns) in the database without corresponding entries in the `django_migrations` table. To fix this, the conflicting schema fragments were manually dropped or renamed back to their legacy states via SQL scripts. Then, the corrupted 0028+ migration files were deleted and regenerated cleanly. A discrepancy in `models.py` was also identified—where `bancarizador` and `cnpj_bancarizador` had been unintentionally removed—and corrected before the final new migration was applied successfully.

### Database Schema Out of Sync
- **Problem/Goal:** `AquisicaoManual` and its staging equivalent were missing the `complementary_data` column in the actual Postgres database, meaning the new code for extra columns would crash on insert.
- **Decision:** Given the corrupted state of the Django migrations history due to a recent rollback, the safest approach was to manually drop the conflicting columns and tables directly in PostgreSQL and recreate a clean Django migration from scratch.
- **Changes:** Ran intermediate SQL dropout scripts (`cleanup_db.py`, `cleanup_db_2.py` etc.) to drop orphaned columns (`tipo_instrumento_id`, `cnpj_emissor`) and tables (`aquisicao_extra_cols`, `cadastro_tipo_instrumento`). Deleted migrations `0028` onwards.

### Legacy Column Preservation
- **Problem/Goal:** During the generation of the new migration, it was observed that the `models.py` for `AquisicaoManual` had lost the `bancarizador` and `cnpj_bancarizador` columns.
- **Decision:** The specification requires these columns to remain. They must be added back to `models.py` before finalizing the migration.
- **Changes:** Restored `bancarizador` and `cnpj_bancarizador` to `AquisicaoManual` and `AquisicaoManualStaging` in `domains/aquisicao/repositories/models.py`.

### Migration Application and Unique Constraint Fix
- **Problem/Goal:** The new `0028` migration failed to apply because it attempted an `AlterUniqueTogether` operation on `DocumentsFolderResult` using a field (`contrato`) that had already been deleted in migration `0021`.
- **Decision:** Since the unique constraint on `contrato` was already dropped in a previous raw SQL migration, the `AlterUniqueTogether` generated by `makemigrations` was redundant and causing an error.
- **Changes:** Manually edited the newly generated `0028_aquisicaoextracols_and_more.py` to remove the `AlterUniqueTogether` block for `DocumentsFolderResult`. The migration then applied successfully.

Key outputs:
- `domains/aquisicao/repositories/models.py` — Restored legacy `bancarizador` fields.
- `migrations/aquisicao/0028_aquisicaoextracols_and_more.py` — Clean, successfully applied migration introducing `complementary_data` and extra column models.

## Key Decisions
- **Manual Schema Cleanup:** Chosen to manually execute `DROP COLUMN` and `DROP TABLE` commands for conflicting entities rather than trying to fake backwards migrations, as the `django_migrations` table was already out of sync with the actual db state.
- **Legacy Field Preservation:** Re-asserted that `bancarizador` must remain on `AquisicaoManual` for backwards compatibility, fixing an unexpected deletion in the models file.
- **Migration Editing:** Edited an auto-generated migration file to eliminate a faulty constraint modification that crashed due to relying on a historically deleted field.
