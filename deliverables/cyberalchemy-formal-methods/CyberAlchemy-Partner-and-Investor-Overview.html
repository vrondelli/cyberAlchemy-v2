Why this matters

Business rules get lost between meetings and code

A team can agree on how a workflow should behave and still ship an application that implements a different rule. The gap is often discovered only during review, integration, or production use.

Change becomes hard to assess

When a term or rule changes, people must discover by hand which claims, workflows, tests, and services may be affected.

Evidence is easy to overstate

A green test or formal result can be presented as proof of a larger product claim, even when it covers only one model, fixture, or environment.

Review absorbs the gap

Domain experts, engineers, and risk owners repeatedly reconstruct the chain from a business decision to its implementation.

The business language

First, agree on the business rules

Before generating code, the team needs to agree on what its important words and rules mean.

Definition Pack

The Define process starts from a real business question and records the minimum semantic context required for downstream work:

What is being attempted?

Goal, original business decision, bounded context, intended consumers, constraints, and desired outcome.

What must be understood?

Concepts, exact sources, supporting evidence, meaning owners, and unresolved questions.

Each important ontology record can carry provenance, branch or role, confidence, candidate or promoted state, drift handling, and downstream-use obligations. Business, system, and bridge branches remain separate so that implementation evidence cannot silently redefine business requirement.

Important boundary. An ontology is a navigable and governed map of meaning. Its existence does not make every node canonical, prove a system exists, or authorize implementation.

A precise business rule

Turn a business rule into a precise claim

A FormalClaim records exactly what the rule says, which definitions it uses, and the limits of that claim. A test or proof comes later.

FormalClaim = ( business meaning, explicit accepted-definition closure, formal signature, canonical proposition, meaning-bearing language profile, assumptions and scope, claim ceiling, deterministic identity )

Example: order submission eligibility

Business voice

“An order may be submitted only if it has at least one line and its total is non-negative.”

Formal voice

∀ o : Order · HasLine(o) ∧ HasNonNegativeTotal(o)

Domain-context voice

This proposition governs submission eligibility. It does not claim that an order was persisted, a message was delivered, payment was authorized, or a production system is correct.

Different tools answer different questions

ProfileQuestion it can addressBound that remains
FOL / sorted FOLPrecise predicates over an explicit signatureA language, not an executor
SMTSatisfiability or validity of an admitted projectionUnknown and timeout retain their native meaning
TLA+/TLCTemporal behavior across a declared state machineModel checking is bounded by model and explored state space
AlloyRelational instances and counterexamplesBounded by the exact scope
LeanTheorem checking in an exact formal environmentDoes not show the running implementation preserves the model
SouffléFinite closed-world derivationDepends on exact facts and rules
For the reader. The proposed understanding view would not “translate a formula back into truth.” It would use source-linked explanation nodes—BusinessMeaning, definition binding, signature, proposition, assumptions, ceiling, dependencies, projections, and evidence. Each node explains one part while the original FormalClaim retains semantic identity.

Checks we can reuse

Which checks carry over to a new application?

Generated code does not begin from an unexamined template. It begins from admitted, versioned realization contracts—but reusable evidence must not be confused with proof of a new application.

What is already checked

Formalized roles

Each meta-type has machine-checkable formation criteria and typed edge-participation rules. The active backend language contains 13 roles and 31 governed relationship signatures.

Admitted realizations

Each active role has one selected TypeScript, Python, and Rust realization: 39 exact, digest-bound realization rows exercised by deterministic generation and bounded static conformance.

Graph-bound proof

For an exact compiled project, DomainSpec can generate a Lean proof unit covering applicable DS-D8 graph obligations and selected L1 structural facts, then check the resulting certificate independently.

Why this helps. A generated project starts from a pre-qualified, content-bound construction basis. Applicable structural obligations can be discharged by fresh replay of the reusable proof and conformance machinery instead of being rediscovered manually.
Still needs fresh checks. EVF may count only evidence bound to the new project’s exact source, graph, realization rows, generated bytes, assumptions, provider, environment, and obligation IDs. New composition, integration, runtime, and business obligations still require their own current evidence. The result, when the required join closes, is PASS_BOUNDED for named obligations—not “all generated code is proven.”

Generated application

What DomainSpec generates

DomainSpec compilation answers a concrete question: “Given this exact authored model, what system structure follows from it, what must a realization provide, and how can we identify the result?”

What the compiler does

Input

Exact AlchLang and DomainSpec declarations: typed concepts, allowed relationships, FormalClaim bindings, integration requirements, and profile selections.

Work

Resolve names, reject missing or invalid endpoints, check type–relationship compatibility, select exact realization contracts, and derive required obligations.

Output

A content-identified compiled graph, readable projections, system ontology, implementation plan or artifacts, and receipts binding all outputs to their inputs.

An example from the compiler

Authored source: Rule OrderCanBeSubmitted --enforces--> Operation SubmitOrder Operation SubmitOrder --produces--> Event OrderSubmitted DomainSpec checks: • both referenced nodes exist • “enforces” accepts Rule → Operation • “produces” accepts Operation → Event • the selected target has realizations for all three roles Compiler products: • graph: exact nodes and typed edges • obligation: SubmitOrder must be guarded by OrderCanBeSubmitted • system ontology: trace from business nodes to system roles and residue • receipt: hashes of source, profile, compiler, graph, and generated output

The compiled graph is the machine’s resolved model. The system ontology is the inspectable traceability projection of that model. Generated code is one selected realization. None of these is allowed to contradict or independently redefine the authored source.

The generated code still needs a runtime

A runtime profile separately selects a target such as TypeScript, Python, or Rust; a provider pack; capability-to-provider mappings; and symbolic configuration or secret slots. The domain model does not change when PostgreSQL is exchanged for another compatible persistence provider. Runtime observations also stay separate: application commit, provider acceptance, delivery, consumer commit, and business completion do not imply one another.

Testing and formal tools

How the application is checked

In the proposed full chain, DomainSpec identifies what needs checking, TDE derives reproducible cases for a supported executable slice, and a selected tool runs those cases. The general integration is still partial.

From a rule to a check

1
DomainSpec obligation: “The SubmitOrder realization must apply OrderCanBeSubmitted before the state-changing commit.”
what must hold
2
TDE derivation: generate neutral cases such as an empty order being rejected, a valid order being admitted, and no rejected case producing a commit or event.
what to check
3
Provider execution: translate those neutral cases into an exact TypeScript test, Python test, Rust test, solver query, or other admitted provider request.
what happened

What TDE does and does not do

current FormalClaim + capability assessment + preservation-backed executable projection → provider-neutral obligations and bounded cases

A neutral obligation carries stable identities, normalized inputs, expected relations or oracle requirements, provenance, residue, and a claim ceiling. It deliberately contains no TypeScript, Python, Rust, Lean, SMT, Alloy, TLC, or Soufflé branch. This lets the same obligation be realized by more than one provider without turning provider syntax into business meaning.

Choose the right kind of check

executable-bounded solver-admissible proof-provider-required unsupported indeterminate

Only an admitted executable-bounded slice enters ordinary test derivation. The theorem route, solver route, temporal model-checking route, relational route, and Datalog route remain distinct.

What each tool actually checked

A provider-runtime binding identifies the provider version and digest, source artifact, command, environment allowlist, fixtures, resource limits, network policy, timeout, and supported result meanings. Raw output remains reachable.

TLA+/TLC route

A FormalClaim with temporal semantics is projected into a declared state model and properties. TLC can report behavior within the explored state space. It cannot establish correctness outside that model or show that implementation code preserves the model.

Lean route

An exact theorem statement and environment are checked through a theorem-provider request. A checked theorem is evidence about that model and binding—not proof of runtime correspondence.

Executable route

TDE derives cases; a selected runtime executes them; the result is bounded by the code, fixture, environment, and observation boundary.

Cross-provider discipline

Provider agreement is non-voting. Several weak results cannot vote themselves into a stronger claim; disagreement, unknown, missing, or stale evidence remains visible.

When a check cannot run. Unsupported, timeout, malformed, stale, unknown, provider error, and missing prerequisites never become PASS through aggregation.

Evidence

What the evidence actually supports

The EVF design checks whether each declared obligation has the right current evidence and shows what is still missing or unresolved. The general end-to-end join remains partial.

For each reachable path p: desired residue ρ(p) exists owner(p) exists obligations O(p) are explicit required evidence kinds K(p) are explicit current evidence E(p) is digest-bound supported(p) only if every obligation and required evidence kind has current positive evidence, comparable under a non-inflating join, with no contradiction, stale input, structural defect, or authority defect.

Different checks answer different questions

Evidence kindAnswersDoes not establish alone
Specification closureDid we describe the declared paths and obligations?Implementation or behavior
Formal proofDoes a proposition follow from an exact model?Implementation preservation
Bounded explorationDoes a property hold in a finite declared state space?Behavior outside the bound
Implementation testWhat did code do for named inputs and environment?Exhaustive or live-system behavior
Runtime observationWhat happened in one named execution?Universal or future correctness
Operational controlDid the system stop, retain, reconcile, alert, or escalate?Internal code correctness

Possible results

PASS_BOUNDED NON_PASSUNSUPPORTEDINDETERMINATE STALEMISSINGFAILEDBLOCKED

A positive conclusion is bound to the exact claim, projection, assumptions, provider, environment, inputs, result semantics, and source identities named by the join. EVF produces candidate-readiness evidence; it does not approve the product.

A passing check is useful only when we can see which source, assumptions, generated code and environment it covered.

Which checks follow from the order rule?

Here is the concrete step between the rule on the previous page and a test run. These are illustrative cases, not output already emitted by the current FormalClaim-to-TDE integration.
